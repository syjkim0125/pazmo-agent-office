# ai-workflow-kit 핸드오프 — ADK 설계 개념만 적용

2026-09-21 사용자 정정 반영. **이전 문서의 ADK SDK·런타임 도입 요구를 철회하고 이 문서로 대체한다.** 사용자는 ADK의 설계 개념을 기존 kit에 적용하려는 것이다. 이 문서는 구현 완료나 인증/G3/G4 승인 기록이 아니다. Office 세션은 kit 원본이나 ADK 의존성을 수정하지 않았다.

아래 내용을 ai-workflow-kit 담당 세션에 전달한다.

$workflow

이전 핸드오프에 ADK 도입 지시가 있었다면 정정한다. **Google ADK를 설치하거나 실행 엔진으로 도입하지 말고, 그 설계 개념만 기존 ai-workflow-kit에 적용해줘.** 현재 저장소와 진행 중인 변경을 먼저 확인하고 보존해줘. Jira는 생성하지 않아도 된다.

## 의도와 경계

ai-workflow-kit는 에이전트가 일을 진행하는 공통 방법을 제공한다. 작업을 명확한 단계로 나누고 입력·출력·의존관계·조건 분기·검증·피드백·사람 확인을 연결하는 graph engineering 개념을 현재 스킬·문서·체커·실행 환경에 맞게 적용한다.

Agent Office는 kit를 사용하는 조직 운영 애플리케이션이다. PM·팀장·Developer·Reviewer에게 역할과 작업을 배정하고, 각자의 실행과 메시지 전달·공유 자원·사용자 접점을 관리한다. 각 agent는 kit의 자기 역할에 필요한 흐름을 사용하고 서로 질문·검토·수정 요청을 주고받아 목표를 달성한다.

업무 절차와 검증 규칙은 kit에서 일관되게 정의한다. 실제 실행·상태 보존은 기존 host의 기능과 책임에 맞춰 연결한다. 이 요구 때문에 kit를 새 독립 서버나 범용 실행 엔진으로 전환하지 않는다. Office에도 동일한 업무 규칙을 별도로 복제하지 않는다.

## 가져올 개념

- 노드: 책임과 입력·출력·완료 근거가 명확한 작업 단위.
- 연결과 분기: 다음 단계를 결정하는 조건과 의존관계. 성공·실패·질문·사람 대기를 구분한다.
- 순차·병렬·합류: 의존하는 작업은 순서대로, 독립적인 작업은 host가 지원하는 범위에서 병렬로 진행하고 필수 결과를 모아 판단한다.
- 제한된 피드백 루프: 리뷰/검증 실패의 근거를 다음 수정에 전달하고 반복 한도와 사람에게 넘기는 조건을 명시한다.
- 역할별 하위 흐름: 공통 절차를 재사용하되, 모든 agent가 전체 workflow를 처음부터 반복하거나 조직을 재귀적으로 생성하지 않는다.
- 상태·대화·산출물·학습의 분리: 현재 진행 상태, 질문/답변 이력, 특정 변경본, 이후 재사용할 검증된 교훈을 구분한다.
- 사람 확인과 재개: 어떤 질문/계약/변경본에 대한 답변인지 확인한 뒤 이어간다. 답변 도착만으로 승인을 간주하지 않는다.

ADK 명칭과 API를 그대로 복제할 필요는 없다. 위 개념을 kit의 기존 용어·구조에 대응시키고, 문서·스킬·체커로 해결할 부분과 기존 host가 실행할 부분을 명시해라. 프롬프트의 권고와 코드가 강제하는 조건도 구분해라.

## 도입하지 않을 것

- Google ADK SDK, ADK 런타임, Google Cloud/Gemini 의존성.
- 다른 그래프 프레임워크나 자체 ADK 복제 엔진.
- 이 요청을 이유로 한 새 서버·DB·메시지 브로커·모델 provider·인증 방식.
- 기존 kit와 Office의 검증된 기능을 버리는 전면 재작성.

별도 인프라가 필요하다고 판단되면 필요성을 먼저 설명하고, 이 요청의 자동 승인 범위로 취급하지 않는다. 기존 모델 호출 방식과 실행 환경을 유지한다.

## 역할별 적용 예시

- PM: 요청 분석 → 필요한 질문 → 답변 반영 → 요구사항 계약 제안.
- 팀장: 요구사항·저장소 문맥 검토 → 작업 분해·의존관계·담당 역할 제안 → 인계.
- Developer: 승인된 작업·피드백 확인 → 구현 → 자체 검사 → 변경본과 근거 제출.
- Reviewer: 대상 변경본·검증 근거 확인 → 검토 → 통과 또는 구체적인 수정 요청.

각 역할의 완료와 전체 목표의 완료는 구분한다. 자체 검사가 독립 리뷰를 대체하지 않으며, 결과가 변경되면 필요한 재검증을 수행한다. 역할별 진입 방식은 현재 kit에 맞는 최소한의 형태로 제공한다. 이름만 다른 거대한 프롬프트 네 개를 만들지 않는다.

## Office에 전달할 계약

Office가 역할과 작업 문맥을 전달하면 agent가 어떤 kit 흐름을 사용하고 무엇을 반환해야 하는지 정의한다. 새 API/서버를 전제로 하지 말고 기존 구조에 맞는 문서·구조화된 결과·필요한 최소 코드로 표현한다.

- 입력: 작업 식별자, 역할, 현재 단계, 요구사항·계획·대상 변경본, 이전 질문/답변·리뷰 근거, 실행 제약.
- 출력: 단계 결과, 산출물 참조, 검증 근거, 질문 또는 수정 요청, 다음으로 필요한 행동, 실패/대기 이유.
- 인계: 발신/수신 역할, 질문과 답변의 연결, 대상 작업·변경본의 일치 여부.
- 상태 책임: kit는 단계/전이의 의미와 규칙을 정의하고, Office 등 host가 권위 있는 상태와 승인 기록을 보존·적용한다. 같은 상태를 두 곳에서 독립적으로 확정하지 않는다.
- 실행 제약: Office의 전역 슬롯·수정 횟수·취소 정책을 agent 내부 반복으로 우회하지 않는다. 일반 kit에는 Office 전용 값을 하드코딩하지 않는다.

G1/G3/G4, Story/Task·M/V 연결, checker, 단순화·리뷰·재검증·Compound를 유지한다. 모델의 자기 보고나 에이전트끼리의 합의가 사람의 승인을 대체하지 않는다.

## 현재 소비자 참고

Office에서 확인한 kit 설치본은 3.1.1이며 kit 원본 저장소의 최신 상태라는 뜻은 아니다. Office 기준 checkpoint는 `codex/office-runtime-baseline`의 `fc55dc8688556586df2e7b9b5a9b1c929311648e`다.

Office에는 요청·역할 대화 저장, 팀장 제안의 Task 등록, 계약/승인, 실행 예산, 격리된 실행 연결, 동일 변경본의 테스트·리뷰, 제한된 수정과 로컬 인도 기반이 있다. 실제 모델 협업은 아직 미검증이다. 이 세션은 kit만 담당하고 Office 저장소는 수정하지 않는다. 기존 Office 기능을 활용할 수 있도록 규약과 연동 예제를 전달한다.

## 검증과 인도

1. 현재 kit의 관련 스킬·문서·체커가 동일한 단계와 전이 규칙을 가리키는지 확인한다.
2. 정상 흐름, 필요한 질문, 리뷰 실패→수정→재검증, 반복 한도, 사람 승인 대기를 구체적인 사례로 검증한다.
3. 오래된 변경본의 리뷰, 중복 답변, 취소된 작업의 결과로 진행하거나 완료하지 못하는지 kit와 host 각각의 검증 책임을 명시한다.
4. standalone 사용과 Office 역할별 사용이 같은 규칙을 따르고 전체 workflow를 중복 실행하지 않는지 확인한다.
5. 검증된 교훈을 다음 관련 작업에서 조회·사용하는 경로를 확인한다. 이를 모델 자동 재학습으로 부르지 않는다.
6. 문서/체커 검증, 모의 실행, 실제 에이전트 실행, 실제 사용자 승인을 구분해 보고한다. 개념 정리만으로 실제 협업 실행을 검증했다고 주장하지 않는다.

Office 담당 세션에 넘길 결과는 변경 요약, kit 버전/commit, 역할별 진입 예시, 입력·출력과 인계 규약, kit/host 책임표, 호환성 영향, 검증 결과와 미구현 사항이다.

먼저 현재 kit와 위 개념의 차이를 짧게 설명한 뒤 기존 승인 범위에서 계획·구현·단순화·리뷰·검증·Compound를 진행해줘. 새 고위험 결정만 구체적으로 확인하고, npm 공개 게시와 main 병합은 별도 요청 없이 하지 마.
