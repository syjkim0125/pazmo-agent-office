## 결정할 내용
작업자가 코드와 테스트를 바꾸더라도 사람의 승인 기록과 완료 판정은 바꿀 수 없게 controller·worker·verifier 권한을 분리한다. 먼저 현재 macOS/Codex의 실제 격리 시험으로 경계를 확인하고, 통과 전에는 Office의 모델 실행을 잠근다.

예: 구현자가 테스트를 수정해 성공을 보고해도, controller가 고정한 같은 후보의 검증과 사람의 G4가 없으면 완료로 전환되지 않는다. 승인 후 후보가 바뀌면 재검증과 재승인이 필요하다.

## 대안과 선택 이유
- 선택안: 기존 Claw 단일 큐를 유지하며 OS가 강제하는 접근 제한을 검증한다. 현재 환경에서 시작할 수 있고 별도 scheduler를 만들지 않는다.
- 대안: 별도 OS 계정/컨테이너를 처음부터 도입한다. 현재 설치·인증 전달·호스트 운영 범위가 추가되므로 native 격리가 부족할 때 새 설계로 검토한다.
- 프롬프트나 worktree만으로 승인 DB를 보호하는 방식은 M4를 충족하지 못한다.

## 실패·복구·검증
- 홈·다른 저장소·승인 DB·제어 API·프로세스·소켓·중첩 Codex 접근을 실제 canary로 시험한다. 모의 시험은 실제 경계 증거로 인정하지 않는다.
- 한 항목이라도 입증하지 못하면 live 자율 실행을 차단한다. 자동으로 다른 provider나 권한 없는 실행으로 우회하지 않는다.
- 초기 DB는 격리된 신규 데이터이며 migration 전 백업한다. 실패 시 시작을 중단하고 이전 runtime/백업으로 복구한다.
- 후보 변경·실패·unknown·충돌·예산 소진·취소/재시작·UI/API 우회 전이를 별도로 시험한다.

## 승인 기록
사용자에게 권한 분리, 실제 격리 시험 전 실행 잠금, 격리 부족 시 별도 계정/컨테이너 검토, 별도 데이터 및 복구 원칙을 설명했다. 사용자는 “응 그렇게 해.”라고 승인했다. 이 응답으로 본 설계와 U2–U8 구현을 진행한다. native 격리 통과나 G4 승인으로 간주하지 않는다.
