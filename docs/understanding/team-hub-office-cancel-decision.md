## 사용자 요청 (2026-10-13)

PR #18 G4 뒤에 "이후에 office에서 거절이랑 취소도 가능하도록 다음 작업 하자." 지금은 Office에서 상대 PM의 질문·범위 승인(G1)·계획 재개에 **승인만** 할 수 있고, 거절과 요청 취소는 허브 요청 화면에서만 한다. D17은 "보낸 요청을 Office에서 취소하는 것"을 실패해야 하는 동작으로 정했다. 이 결정은 그 불변 조건을 바꾼다.

## 사용자 결정 (설명 페이지 https://claude.ai/artifact/TbRW7XWvrV4XgsmrVH9JYp 확인 후)

| 질문 | 선택 |
|---|---|
| "거절"의 뜻 | **요청 취소와 같다.** 지금 허브 화면과 받는 쪽 Office에서 질문·G1의 2번이 요청 전체를 취소하는 것과 같은 뜻이다. "고쳐서 다시 와"(범위 재작성)는 택하지 않았다. |
| 취소 위치 | **Decisions 항목과 카드 버튼 둘 다** |
| 취소 경로 | **새 연결 API로 허브에서 바로 취소.** 답변 2번을 맡은 Office에 넘기는 방식은 택하지 않았다. |

## 결정

1. **의미.**
   - Office의 "요청 취소"는 허브 요청 화면의 **요청 취소**와 같은 동작이다.
   - 허브는 요청을 `cancelled`로 바꾸고, 열린 배정을 `cancelled`로 끝낸다.
   - 맡은 사람의 Office는 다음 확인(5초)에서 종료 이벤트를 받아 로컬 작업을 멈춘다. 이 경로는 1단계 그대로다.
   - 받는 쪽 동작은 바꾸지 않는다.
2. **위치.**
   - **Decisions:** `팀 허브 · <레포> · …` 항목(질문, 범위 승인(G1), 계획 재개)의 선택지를 두 개로 한다.
     - 1번: 지금처럼 승인 또는 답변 제출.
     - 2번: 새로 추가하는 **요청 취소**.
   - **카드:** `↗ <레포> · <상태>` 표시 바로 옆에 작은 **✕(보낸 요청 취소)** 버튼을 둔다. 표시 자체는 지금처럼 허브 요청 페이지로 가는 링크로 남긴다. (구현 계획 단계 정정, 2026-10-13: 처음 문서는 "표시를 누르면 요약과 허브 링크가 나오고 거기에 버튼"이었으나, 표시가 이미 허브 링크라서 칩 옆 버튼으로 바꿨다. 동작·조건은 같다.)
     - 상태가 대기, 맡음, 실행 중, 답변 대기일 때만 보인다. 완료·취소된 요청에는 없다.
     - 아직 아무도 맡지 않은 요청도 취소할 수 있다.
   - 두 위치 모두 이 Office가 허브에 연결돼 있고 live일 때만 동작한다.
3. **확인.**
   - 누르면 확인창을 한 번 띄운다. 문구: "요청을 취소하면 되돌릴 수 없어요. 상대 쪽 작업도 멈춥니다."
   - 사유 입력칸은 두지 않는다. 허브 취소에도 사유가 없다 (ASSUMED).
4. **경로.**
   - 두 버튼 모두 Office 로컬 API → 연결 모듈 → 새 연결 API `outgoing-cancel` → 허브의 기존 `cancel` 순서로 간다.
   - Decisions 2번을 답변으로 맡은 Office에 넘기지 않는다. 그러면 맡은 Office가 꺼져 있을 때 취소가 늦어지고, 취소 경로가 둘로 갈린다.
5. **연결 토큰 권한.**
   - 같은 토큰에 **보낸 요청 취소 하나만** 더한다.
   - 범위는 D17의 보낸 요청 조회와 같다: (요청자 = 이 연결의 팀원, 보낸 곳 레포 = 이 연결의 레포).
   - 허브 웹페이지에서 보낸 요청, 같은 사람이 다른 레포의 Office에서 보낸 요청, 남의 요청은 취소할 수 없다.
   - 수락, 반납, 승인 외 답변, G4, diff는 여전히 할 수 없다.
   - 연결 답변 API(`outgoing-answer`)는 계속 1번만 받는다. 취소는 `outgoing-cancel`로만 한다.
6. **버전.**
   - 프로토콜 번호는 `2`로 둔다 (ASSUMED).
   - 새 경로를 모르는 허브는 404 `NOT_FOUND`를 돌려준다. Office는 이를 `HUB_UPGRADE_REQUIRED`로 바꿔 "허브를 업데이트해야 취소할 수 있습니다"를 보여 준다.
   - 보내기·조회·승인은 계속 동작한다.
7. **경계는 그대로다.**
   - Office는 `127.0.0.1`에만 열린다. 허브 토큰은 Office 서버에만 있다.
   - 로컬 취소 API는 화면 세션의 쓰기 토큰(CSRF)을 요구한다.
   - Office의 보낸 기록은 허브가 취소를 응답한 뒤에만 `cancelled`로 바꾼다.

## 실패 처리

| 상황 | 동작 |
|---|---|
| 이미 완료·취소된 요청 | 허브가 409 `STATE`를 돌려준다. "이미 끝난 요청이에요"를 표시하고 보낸 기록을 새로 고친다. |
| 허브 꺼짐 | "허브에 연결할 수 없습니다"를 표시한다. 기록은 바꾸지 않고 자동 재시도도 하지 않는다. |
| 옛 허브(새 경로 없음) | "허브를 업데이트해야 취소할 수 있습니다"를 표시한다. 다른 기능은 그대로 쓴다. |
| 응답 유실 뒤 다시 누름 | 이미 취소된 요청이면 409로 "이미 끝난 요청이에요"가 된다. 중복 부작용은 없다. |
| 범위 밖 요청(허브에서 보냈거나 다른 레포 Office에서 보냄) | 허브가 404로 거부한다. 항목이나 버튼이 화면에 나오지 않는 것이 정상이다. |
| 상대가 막 인도한 순간에 취소 | 허브 화면에서 취소할 때와 같다. 맡은 Office에서 이미 인도된 결과는 그쪽에 남고, 허브 요청은 취소로 표시된다. 바꾸지 않는다. |
| 채팅으로 보낸 요청 | 카드가 없다. 상대 질문·G1이 Decisions에 떴을 때 그 항목에서 취소하거나, 허브에서 취소한다 (ASSUMED). |

## 불변 조건과 예시

예: eevee-be Office(관리자)가 hub-test-backend로 "README 한 줄"을 보냈다. 상대 PM이 올린 범위 승인(G1)이 eevee-be Decisions에 뜬다. 관리자는 범위가 틀렸다고 보고 **요청 취소**를 고르고 확인창에서 확인한다. 그러면 다음이 일어난다.
- 허브 요청이 취소로 바뀐다.
- 시험 Office의 작업이 5초 안에 멈춘다.
- eevee-be 카드는 `↗ hub-test-backend · 취소`가 되고, Decisions 항목은 사라진다.

다음은 모두 실패해야 한다.
- 연결 토큰으로 허브 페이지에서 보낸 요청, 다른 레포 Office에서 보낸 요청, 남의 요청을 취소하는 것
- 완료된 요청을 취소하는 것
- CSRF 토큰 없이 로컬 API로 취소하는 것
- 화면이 허브 토큰을 받는 것
- `outgoing-answer`로 1번 외 선택을 보내는 것
- 연결 토큰으로 수락·반납·G4 답변을 하는 것

## 범위

- **이번:**
  - 허브: 연결 API `outgoing-cancel`(범위 검사 + 기존 `cancel`)
  - Office: 게이트웨이 `cancel`, 로컬 API `POST /api/hub/outgoing/:requestId/cancel`(CSRF), Decisions `hubout:` 항목 2번 "요청 취소"
  - 화면: 카드의 보낸 요청 취소 버튼, 두 위치의 확인창, 오류 문구
- **제외:**
  - "고쳐서 다시 와"(범위 재작성 루프)
  - 취소 사유 입력
  - 채팅으로 보낸 요청의 목록 화면
  - 취소된 요청 되살리기
  - 받는 쪽 동작 변경
  - 알림
- **다음 Story 후보:** Lead 초안(D), 에이전트 간 Q&A

## 검증 (V12)

- 자동 테스트로 확인한다.
  - 허브: 연결로 취소. (팀원, 보낸 곳 레포) 범위 밖은 404, 완료·취소된 요청은 409, 남의 요청 거부. `outgoing-answer`는 1번만. 프로토콜 1에서는 426.
  - Office: 게이트웨이 취소와 기록 갱신, 404를 업데이트 필요로 바꾸기, 허브 꺼짐. 로컬 API CSRF. Decisions 2번이 취소로 가고 항목이 사라지는 것.
  - 화면(vitest): 카드 버튼의 표시 조건(상태별), 확인창, 오류 문구, Decisions 2번.
- 기존 테스트는 전부 통과해야 한다. Office `127.0.0.1` 단언도 유지한다.
- 실제 확인: 이 Mac에서 Office 두 개로 다음 두 가지를 확인한다.
  - (a) eevee-be에서 보낸 요청을 상대 수락 뒤 **Decisions의 요청 취소**로 취소한다. 상대 작업이 멈추고 카드가 취소가 된다.
  - (b) 새로 보낸 요청을 아무도 맡기 전에 **카드 버튼**으로 취소한다.
- 보안을 포함한 브랜치 전체 리뷰 1회. 결과는 X/X로 보고한다.

## 대안과 복구

- "고쳐서 다시 와": 받는 쪽에도 없는 새 흐름이다. PM 재작성 루프, 횟수 제한, 기록 방식을 새로 설계해야 해서 택하지 않았다.
- 답변 2번을 맡은 Office로 넘기기: 맡은 Office가 꺼져 있으면 취소가 늦고, 카드 버튼과 길이 둘로 갈려 택하지 않았다.
- 프로토콜 `3`으로 올리기: 감지 단계가 하나 늘어난다. 404 감지로 충분해서 택하지 않았다 (ASSUMED).
- 복구: 새 경로와 버튼을 빼면 D17 동작(승인만)으로 돌아간다. 취소된 요청은 되살릴 수 없다.
