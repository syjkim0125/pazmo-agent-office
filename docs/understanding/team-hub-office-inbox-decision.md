## 사용자 요청 (2026-10-15~16)

Fusion 실제 확인 중에 사용자가 이렇게 물었다. "아니 왜 또 요청 수락이 허브에서 하도록 변경된거야? 본인 오피스의 task에서 보도록 할 수 있는거 아냐?" 그리고 "요청받은거는 Inbox에 나오는거지?"라고 확인했다. 사용자는 실제 확인을 마친 뒤 다음 묶음으로 진행하기로 정했다.

## 지금 상태 (코드 근거)

- 허브 요청 상태는 `open`/`accepted`/`done`/`cancelled`다(`src/hub/store.ts` 스키마).
  - 수락은 그 레포 담당자 누구나 할 수 있고, 먼저 한 사람이 맡는다(`accept`, 진행 중 배정 유일 인덱스).
  - 맡은 사람의 반납(`release`)과 요청자 취소(`cancel`)만 있다. 거절은 없다.
- 수락은 허브 웹(`POST /requests/:id/accept`)에서만 할 수 있다.
- Office 연결 토큰은 `GET /api/link/work`로 **수락된 배정만** 받는다.
  - 받은 배정은 `submitFromHub`가 Inbox 상태의 작업으로 만들고(`pazmo_hub_requests`에 기록), PM이 시작한다.
  - 대기 중 요청은 Office에 보이지 않는다.
- 다른 허브로 다시 연결해도 이전 허브에서 받은 작업은 아무도 정리하지 않는다.
  - 2026-10-15 실제 확인에서 시험 Office에 10/13 작업 하나가 `pending`으로 남아 있었다.

| 질문 | 선택 |
|---|---|
| 거절의 뜻 | **요청을 닫는다.** 사유(선택)가 요청자의 Office 카드와 허브에 보이고, 같은 레포의 다른 담당자도 더는 맡을 수 없다. |
| 다른 허브로 교체할 때 이전 허브 작업 | **확인 후 취소.** 교체 확인 칸에 건수를 보이고, 연결이 성공한 뒤 이 Office에서 취소한다. |
| 접근 | **받은 요청 목록을 따로 두고, 수락하면 지금 흐름을 그대로 탄다.** 대기 중 요청을 작업 표에 섞거나 Decisions로 보내는 방식은 택하지 않았다. |
| 진행 | "진행해" (2026-10-16) |

## 결정

1. **허브 연결 API 추가.** 프로토콜 2이고, 토큰은 그 팀원·그 레포 범위다.
   - `GET /api/link/incoming`: 그 레포의 `open` 요청 목록을 준다. 항목은 요청 ID, 요청자 이름, 보낸 레포 이름(있으면), 출처, 본문, 위험도, 만든 시각이다. 50건까지 오래된 것부터 준다.
   - `POST /api/link/incoming-accept {requestId}`: 허브의 `accept`와 같은 규칙으로 처리한다. 먼저 맡은 사람이 있으면 409 `ALREADY_ACCEPTED`다.
   - `POST /api/link/incoming-decline {requestId, reason?}`: 담당자만 할 수 있고, `open`일 때만 된다. 요청을 `cancelled`로 닫고 `closed_by`(팀원)와 `close_reason`(`declined`)과 `close_note`(사유, 500자까지)를 남긴다. 다른 상태면 409다.
   - 옛 허브에 새 경로가 없으면 Office는 "허브를 업데이트해야 받은 요청을 볼 수 있습니다"를 보인다(D18 방식).
2. **허브 저장과 화면.**
   - `hub_requests`에 `closed_by`, `close_reason`, `close_note` 칸을 더한다(`ALTER TABLE ADD COLUMN`, 상태 CHECK는 그대로).
   - 허브 요청 화면의 담당자에게 [거절] 버튼과 사유 칸을 둔다. 거절된 요청은 "거절됨 · 사유 · 거절한 사람"으로 보인다.
   - 요청자의 보낸 요청 조회(`outgoing`)에 거절 여부와 사유를 넣는다.
3. **Office 받은 요청.**
   - 게이트웨이가 5초 동기화 때 `incoming`을 가져와 메모리 또는 로컬 표에 둔다.
   - 로컬 API는 다음과 같다. 모두 세션 CSRF가 필요하고, live에서만 동작한다.
     - `GET /api/hub/incoming`
     - `POST /api/hub/incoming/:id/accept`
     - `POST /api/hub/incoming/:id/decline {reason}`
   - 화면:
     - Tasks Inbox 열 맨 위에 "받은 팀 허브 요청" 묶음을 둔다. 카드마다 요청자·보낸 레포·내용 앞부분·위험도와 [수락] [거절]이 있다. 작업 표에는 들어가지 않는다.
     - 수락하면 "수락했습니다. 곧 Inbox에 작업으로 들어옵니다"를 보인다. 다음 동기화에 기존 경로(`work` → `submitFromHub`)로 작업이 생긴다.
     - 거절할 때는 화면 안 확인 칸에서 사유를 받는다. `window.confirm`은 쓰지 않는다.
   - 보낸 쪽 카드는 거절된 요청에 "거절됨 · 사유" 칩을 보인다.
4. **다른 허브로 교체.**
   - 연결 창의 교체 확인 칸에 "이전 허브에서 받은 진행 중 작업 N건이 취소됩니다"를 더한다.
   - 연결이 성공한 뒤에만, 이전 허브 키의 진행 중 작업(`pazmo_hub_requests`에 있고 완료·취소가 아닌 것)을 이 Office에서 취소한다.
   - 연결이 실패하면 아무것도 취소하지 않는다.
   - 같은 허브에 다시 연결할 때(같은 원점)는 취소하지 않는다.
5. **작은 고침.**
   - 연결 창에 초대 링크(`/invite/…`)를 붙여넣으면 이렇게 안내한다. "초대 링크입니다. 허브에 합류한 뒤 내 Office 연결에서 연결 문자열을 만드세요."
   - 허브의 연결 문자열 복사 버튼이 성공·실패를 표시한다. 실패하면 문자열을 선택해 둔다.
6. **경계는 그대로다.**
   - Office는 `127.0.0.1`에만 열리고, 허브는 Office로 접속하지 않는다.
   - 수락·거절은 사람이 버튼을 눌러야만 일어난다.
   - 허브 토큰은 서버에만 있다.
   - 수락 뒤 G1·G3·G4는 맡은 사람의 Office에서 한다.
   - 허브 웹 수락은 남긴다.

## 실패 처리

| 상황 | 동작 |
|---|---|
| 다른 담당자가 먼저 수락 | "이미 다른 담당자가 맡았습니다"를 보이고 카드를 없앤다. |
| 요청자가 그 사이 취소 | "이미 취소된 요청입니다"를 보이고 카드를 없앤다. |
| 담당자에서 빠짐(토큰 무효) | 기존 연결 오류 안내를 따른다. |
| 옛 허브(경로 없음) | "허브를 업데이트해야 받은 요청을 볼 수 있습니다". 보내기·취소는 지금처럼 동작한다. |
| live 아님 | 받은 요청 묶음을 보이지 않는다. 수락 API는 `HUB_NOT_LIVE` 409다. |
| CSRF 없음 | 403 |
| 교체 연결 실패 | 이전 작업을 취소하지 않는다. |

- 자동 시험:
  - 허브:
    - `incoming` 범위(그 레포, `open`만, 다른 레포·남의 요청 없음)
    - 수락 경쟁(먼저 맡은 사람만 성공)
    - 거절 권한·상태와 사유 길이
    - 거절 뒤 수락 불가
    - 요청자 `outgoing`의 거절 표시
    - 허브 웹 거절
    - 프로토콜 1 거부
  - Office:
    - 게이트웨이 incoming 동기화
    - 로컬 API CSRF·live·오류 문구
    - 교체 시 이전 작업 취소(성공 때만, 같은 허브 제외)
    - 초대 링크 안내
  - 화면:
    - Inbox 받은 요청 카드
    - 수락·거절, 화면 안 확인
    - 보낸 쪽 거절 칩
    - 기본 대화상자 없음
- 기존 시험은 모두 통과해야 한다.
- 실제 확인(Fusion):
  1. eevee-be에서 hub-test-backend로 두 건을 보낸다.
  2. 시험 Office의 Inbox에서 하나는 수락해 작업이 생기는지 본다.
  3. 다른 하나는 사유를 써서 거절하고, eevee-be 카드에 "거절됨 · 사유"가 뜨는지 본다.
- 보안을 포함한 브랜치 리뷰를 1회 한다.

## 대안과 복구

- **대기 요청을 바로 Inbox 작업으로 만들기:** 맡지 않은 요청이 작업 표에 섞여 정리가 복잡해서 택하지 않았다.
- **Decisions로 받기:** 사용자가 Inbox를 원해서 택하지 않았다.
- **거절 = 나만 넘김:** 요청자가 거절을 알 수 없어서 택하지 않았다.
- **복구:**
  - 허브 웹 수락이 남아 있으므로, 새 경로와 카드를 빼면 지금 방식으로 돌아간다.
  - 새 칸은 비어 있어도 기존 동작에 영향이 없다.
