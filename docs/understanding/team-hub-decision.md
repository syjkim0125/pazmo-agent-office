# G3 proposal: 초대받은 팀원이 함께 쓰는 사내망 팀 허브 (1단계)

Status: Approved
Understanding gate (G3): user conversation · 2026-10-08 · Check-in: accepted
Story: pazmo-agent-office-contract.md (M8; V10)
Prior approved decisions: cli-runner-selection-decision.md (D15), remote-controller-auth-decision.md, native-runner-isolation-decision.md

## 사용자 요청 (2026-10-07)

Office를 온라인으로 열어 팀원이 들어와 일을 시킬 수 있게 한다. 각자 레포를 연결하면 그 목록이 팀에 공유되고 협업하기 좋아야 한다. 초대받은 사람만 들어올 수 있다.

## 지금 구조에서 막히는 점 (2026-10-07 코드 확인)

- **사람 구분이 없다.** DB에 사람이나 작성자 개념이 없고, 사람은 "CEO" 한 명이다. `pazmo_approvals`는 운영자 토큰 하나에 묶여 있다.
- **레포가 하나다.** Office 한 개는 프로젝트 하나에 묶인다. `--project`마다 데이터 디렉터리가 따로 생기고, 다른 경로를 쓰면 `PROJECT_MISMATCH`로 거부한다.
- **나만 열 수 있다.** 비밀값 하나로 잠겨 있고, `claw-service.ts`가 `HOST=127.0.0.1`을 강제한다.
- **로그인 공유는 약관 위반이다.** 실행은 내 구독 로그인으로 한다. 팀원 요청을 내 구독으로 돌리면 Anthropic 약관이 금지하는 "구독 자격으로 사용자 대신 요청"에 해당한다. OpenAI도 `auth.json` 공유를 금지하고, 자동화에는 API 키를 권장한다. 근거는 `cli-runner-selection-decision.md` "약관 근거"에 있다.

## 사용자 결정 (설명 페이지 https://claude.ai/artifact/DUc2H5K2yRydTeY5pGNWrQ 확인 후)

| 질문 | 선택 |
|---|---|
| 팀원이 시킨 일을 누구 로그인으로 실행하나 | **각자 자기 PC 실행기.** 회사 API 키와 내 구독 공유는 택하지 않음 |
| 누구 PC에서 실행하나 | **맡는 사람이 직접 수락.** 그 사람의 PC와 로그인으로 실행하고 자동 배정은 없음 |
| 공유 서버 위치 | **내 Mac을 사내망에 공개.** 나중에 사내 서버로 옮기기 쉽게 만듦 |
| 로그인 방식 | **초대 링크로 브라우저 등록.** 비밀번호와 외부 설정 없음 |
| 질문·G1·G4를 누가 하나 | **질문·G1은 요청자, G4는 맡은 사람** |
| 구현 방식 | **별도 허브 + 각자 Office 연결.** 지금 Office를 다중 사용자로 바꾸지 않음 |
| 협업 모델과 순서 | **레포 담당제 + 3단계.** 이번에는 1단계만 |

## 결정

1. **허브는 게시판이자 우체국이다. AI를 실행하지 않는다.**
   - 새 명령 `pazmo-office hub`로 띄운다. 터미널에서 실행하고 Ctrl-C로 멈춘다. Office와 분리된 데이터 디렉터리와 SQLite를 쓴다.
   - 저장하는 것: 팀원, 등록된 브라우저, 초대, 레포(이름, 정규화한 git 원격 주소, 담당자), 요청(레포, 본문, 위험도, 요청자, 수락자, 상태, 비어 있는 `parent_request_id`), 진행 이벤트, 질문과 답변.
   - 저장하지 않는 것: 로그인 정보, 레포 전체, 인도물, 실행기, VM.
2. **각자 Office는 지금 경계를 그대로 유지하고, 허브로 나가는 연결만 더한다.**
   - Office는 계속 `127.0.0.1`에만 열린다. 허브는 Office 안으로 들어오지 않는다.
   - 연결 모듈은 허브에 HTTPS로 주기 조회한다(5초, ASSUMED). 수락된 요청은 기존 요청 등록 경로로 넣는다.
   - 진행(단계, 역할 대화 요약, 질문, G1 Story, diff·검사 결과, 보고서, 최종 상태)을 올린다.
   - 요청자의 질문·G1 답변과 취소를 받아 기존 답변·취소 경로로 전달한다.
3. **레포 담당제.**
   - 레포를 등록한 사람이 첫 담당자다. 담당자나 관리자가 담당자를 추가하거나 뺄 수 있다.
   - 그 레포 요청의 수락과 그 레포용 Office 연결은 담당자만 할 수 있다. 요청은 누구나 올린다.
   - Office는 지금처럼 레포마다 하나씩 띄운다. 허브는 git 원격 주소로 연결 상태를 묶는다.
4. **승인 위치.**
   - 질문과 G1은 그 요청의 요청자만 허브에서 답한다.
     - Office는 답변 원문, 답한 팀원 ID와 이름, 시각, 허브 요청 ID를 함께 기록한다.
     - 이벤트 actor는 `human`으로 두고 출처를 `hub:<memberId>`로 표시한다.
     - 질문 revision이나 입력 digest가 현재 값과 다르면 거부한다.
   - G4와 인도는 맡은 사람이 자기 Office 화면에서 한다. 지금 G4 규칙(D13 포함)을 그대로 쓴다. 허브는 G4 결과와 보고서를 보여 주기만 한다.
5. **출입.**
   - 첫 시작 때 터미널에 관리자 초대 링크를 한 번 출력한다.
   - 초대 링크는 관리자만 만든다. 받을 사람 이름을 지정하고, 1회용이며 72시간 뒤 만료된다(ASSUMED). 서버에는 해시만 저장한다.
   - 링크를 열면 그 브라우저가 등록된다. HttpOnly·Secure·SameSite=Strict 쿠키이고, 30일이며 사용할 때마다 연장한다(ASSUMED).
   - 관리자는 팀원이나 브라우저를 회수할 수 있고, 다음 요청부터 바로 거부된다.
   - 쓰기 요청은 CSRF 토큰, Origin, Host를 검사한다. 입력은 64 KiB로 제한한다.
6. **HTTPS.**
   - 허브가 자체 인증 기관과 서버 인증서(설정한 사내망 IP와 호스트 이름)를 만든다. 팀원은 안내에 따라 한 번 신뢰한다. HTTP는 제공하지 않는다.
   - 인증 기관 개인 키는 허브 데이터 디렉터리에 0600으로 둔다.
7. **Office 연결 토큰.**
   - 담당자가 허브의 "내 Office 연결"에서 한 줄 명령(허브 주소, 1회용 코드, 인증서 지문)을 받는다. 자기 PC에서 실행하면 짝이 맺어진다.
   - Office는 그 지문의 인증서만 믿는다. 토큰은 Office 데이터 디렉터리에 0600으로 저장한다.
   - 토큰 범위는 (팀원, 레포 원격 주소) 하나다. 할 수 있는 일은 그 팀원이 수락한 그 레포의 요청 조회, 그 요청의 진행 올리기, 답변·취소 받기뿐이다. 회수할 수 있다.
   - 허브와 Office는 프로토콜 버전을 확인하고, 맞지 않으면 연결을 거부한다.
8. **팀원 요청은 신뢰하지 않는 입력이다.** 네트워크 없는 컨테이너, 읽기 전용 `/candidate/tree`, 원본·main 자동 반영 금지, G4를 그대로 적용한다. 수락은 사람이 직접 한다.

## 실패 처리

| 상황 | 동작 |
|---|---|
| 허브 꺼짐 | 수락된 작업은 Office에서 계속 진행한다. 올릴 진행은 로컬에 쌓았다가 재연결 때 보낸다. 허브는 "마지막 소식 n분 전"을 표시한다. |
| Office 꺼짐 | "수락됨 · 연결 끊김"으로 표시한다. 수락자는 반납할 수 있고, 요청자는 취소할 수 있다. |
| 동시 수락 | 트랜잭션으로 한 명만 수락된다. 나머지는 "이미 맡음"을 본다. |
| 취소 | Office가 기존 `cancel-request`/`cancel-task` 경로로 처리하고, 정리 상태를 올린다. |
| 옛 질문에 대한 답 | Office가 거부한다. 허브는 "질문이 바뀌었어요"로 표시한다. |
| 중복 진행 전송 | 이벤트 ID로 한 번만 반영한다. |
| 버전 불일치 | 연결을 거부하고 맞출 버전을 안내한다. |

쓰기 요청은 자동으로 재시도하지 않는다. 같은 원인으로 진전이 없으면 2회 후 멈춘다. 진행 올리기는 멱등이라 재시도한다.

## 불변 조건과 예시

예: 팀원 B가 eevee-be에 요청을 올리고, 담당자 A가 수락한다. A의 Office가 A의 claude 로그인으로 PM을 돌린다. PM 질문은 허브에 뜨고, B가 답한다. G1도 B가 승인한다. A의 Office가 구현과 검사를 하고, A가 자기 화면에서 G4를 한다. 인도물은 A의 PC에 남는다.

다음은 모두 실패해야 한다.
- 초대받지 않았거나 회수된 브라우저의 접근
- B가 아닌 팀원의 G1 답변
- 담당자가 아닌 팀원의 수락
- 허브가 Office로 접속을 여는 것
- 연결 토큰으로 다른 레포나 남의 요청을 읽는 것
- 허브가 실행기, 로그인 정보, 인도물에 접근하는 것
- 허브에서 G4를 끝내는 것

허브가 탈취되면 G1 답변을 위조할 수 있다. 그래도 인도에는 맡은 사람의 로컬 G4가 필요하다. 그래서 허브만으로는 결과물이 나가지 않는다.

## 범위

- **1단계(이번):** 위 결정 1–8, 화면 다섯 가지(팀원·초대 관리, 레포 목록, 요청 게시판, 요청 상세, 내 Office 연결)
- **2단계(후속 Story):** 연계 요청. Lead가 다른 레포 변경이 필요하면 초안을 쓰고, 사람이 보내고, 상대 담당자가 수락한다. 상대 질문은 요청자 사람이 답한다.
- **3단계(후속 Story):** 상대 에이전트의 사실 질문에 요청 쪽 에이전트가 답한다(최대 2왕복, 보고서 기록). 범위·G1·G4는 사람이 한다. 수락받지 않은 일을 에이전트가 만들거나 남의 구독으로 실행하지 않는다.
- **제외:**
  - 허브에서의 실행, 회사 API 키
  - 캐릭터 채팅, 메일·Slack 알림, SSO, HTTP
  - 사내 서버 배포, 자동 배정
  - 지금 Office의 다중 사용자화

## 검증 (V10)

- 자동 테스트로 확인한다.
  - 초대 1회 사용·만료·회수
  - 권한표: 요청자만 답변·G1, 담당자만 수락, 관리자만 초대
  - CSRF·Origin·Host와 크기 제한
  - 동시 수락, 이벤트 중복, 옛 답변 거부
  - 연결 토큰 범위, 틀린 지문 거부
  - 허브가 꺼졌을 때 쌓기와 재전송, 버전 불일치
- 기존 테스트는 전부 통과해야 한다. Office의 `127.0.0.1` 단언도 유지한다.
- 실제로 확인한다. 내 Mac에 허브를 띄우고 eevee-be Office를 연결한다. 다른 브라우저 프로필로 초대받은 팀원 역할을 한다. 요청 → 수락 → claude 실행 → 허브 G1 → 로컬 G4 → 허브 보고서까지 확인한다.
- 다른 사람의 실제 PC로 하는 시험은 사용자가 준비한다. 그 전에는 "다중 PC 검증 완료"로 보고하지 않는다.
- 별도 보안 리뷰어 1회. 결과는 X/X로 보고한다.

## 사용자가 확인할 것 (Claude가 확인할 수 없음)

- 회사 PC에서 사내망으로 서버를 열고 팀 diff를 저장하는 것이 회사 IT·보안 정책상 허용되는지
- macOS 방화벽 허용과 잠자기 설정 (시스템 설정은 사용자가 직접 바꾼다)
- 맡은 사람이 동료의 요청을 자기 구독으로 실행하는 것: 본인이 수락한 자기 업무로 보는 것은 해석이다. 약관 원문에 이 경우가 직접 나오지는 않는다.

## 대안과 복구

- 회사 API 키로 서버 실행: 비용·승인이 필요하고 D15를 바꾸므로 택하지 않았다. 나중에 허브 옆 실행기로 추가할 수 있다.
- 지금 Office를 다중 사용자로 바꾸기: 업스트림 전반 수정과 공격면 확대 때문에 택하지 않았다.
- 복구: 허브를 끄고 Office 연결을 해제하면 지금 동작과 같다. 허브 데이터는 허브 디렉터리에만 있다.

## 사람의 결정

사용자는 이 문서와 Story 수정안을 검토한 뒤 2026-10-08 "승인, 계획 써줘"라고 답했다. 이 답이 G3 승인이다.

## 승인 범위

- **승인하는 것:** 1단계의 구현·검증, 내 Mac에서 사내망 시험 운영
- **승인하지 않는 것:** 사내 서버 배포, 2·3단계, API 키 실행, 작업 단위 G1/G4 대체, 회사 정책 확인 대체
