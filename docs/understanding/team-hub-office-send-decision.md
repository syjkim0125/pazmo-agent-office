## 사용자 요청 (2026-10-13)

Office 화면(캐릭터 채팅, Tasks)에서 바로 "백엔드 담당자에게 이 일 보내"를 할 수 있게 한다. 1단계에서는 요청을 허브 웹페이지에서만 올릴 수 있다.

## 사용자 결정 (설명 페이지 https://claude.ai/artifact/Pov4FiUhH7uLefXGy7Y7jz 확인 후)

| 질문 | 선택 |
|---|---|
| 누가 보내기를 시작하나 | 사람의 직접 보내기와 Lead 초안 둘 다. **보내기는 항상 사람** |
| 보낸 뒤 원래 작업 | **계속 진행**하고, 연결된 요청의 상태만 표시 |
| Office에서 보내는 방식 | **보내기 창**(Tasks 카드와 채팅창의 버튼). 모델 호출 없음 |
| 상대 PM의 질문·G1에 답하는 곳 | **내 Office Decisions** |
| 순서 | **A(보내기)·B(상태)·C(Office에서 답하기)를 이번에** 한다. D(Lead 초안)는 다음 Story |
| 구현 방식 | **Office가 대신 허브와 대화.** 허브 페이지를 열어 주는 방식과 브라우저가 허브를 직접 호출하는 방식은 택하지 않음 |

## 결정

1. **보내기 (A).**
   - Tasks 카드와 채팅창에 **팀 허브로 보내기** 버튼을 둔다. 이 Office가 허브에 연결돼 있고 live일 때만 누를 수 있다.
   - 창에서 대상 레포(허브 레포 목록), 내용(16,384바이트 이하, NUL 금지, 바이트 카운터), 위험도를 고른다.
   - 제출은 Office 로컬 API → 연결 모듈 → 허브 순서로 간다. 허브는 요청자를 이 연결의 팀원으로, 출처를 `<레포 이름> Office의 작업 '<제목>'` 또는 `<레포 이름> Office 채팅`으로 기록한다(200자 이하).
   - 보낸 작업이 허브에서 온 일이면 `parent_request_id`로 연결한다.
   - 창마다 고유 키(UUID)를 붙인다. 허브는 (팀원, 키)마다 요청을 한 번만 만든다.
   - Office는 허브가 성공을 응답한 뒤에만 보낸 기록을 남긴다. 기록 항목은 허브 요청 ID, 로컬 작업 ID(채팅이면 없음), 레포 이름, 보낸 시각이다.
2. **상태 보기 (B).**
   - 연결 모듈은 5초 주기 확인 때 **이 레포의 Office에서 보낸 요청**의 상태를 함께 받는다. 범위는 (팀원, 보낸 곳 레포)이다.
   - 받는 항목: 상태(대기·맡음·실행 중·답변 대기·완료·취소), 맡은 사람 이름, 4줄 변경 요약, 열린 요청자 결정.
   - diff는 받지 않는다.
   - Tasks 카드에 `↗ <레포> · <상태>` 표시를 붙이고, 누르면 요약과 허브 링크를 보여 준다. 원래 작업은 멈추지 않는다.
3. **Office에서 답하기 (C).**
   - 받은 요청자 결정은 내 Office Decisions에 `팀 허브 · <레포> · PM 질문 / 범위 승인(G1) / 계획 재개`로 띄운다. 대상은 `questions`, `story`, `planning-retry`뿐이다.
   - 답은 연결 모듈이 허브의 요청자 답변으로 전달한다. 허브 웹페이지에서 답한 것과 같은 기록, 같은 규칙(요청자만, 옛 질문 거부)을 적용한다.
   - 상대의 작업 단위 G1/G3/G4와 인도는 맡은 사람의 일이므로 보이지 않는다.
4. **연결 토큰 권한 확장 (프로토콜 2).** 같은 토큰으로 다음만 추가한다.
   - (a) 레포 목록 조회: ID, 이름, 담당자 이름. git 주소는 주지 않는다.
   - (b) 내 이름으로 요청 생성: 대상은 아무 등록 레포이고, 연결당 **시간당 30건**까지다(ASSUMED).
   - (c) (팀원, 보낸 곳 레포) 범위에서 보낸 요청 조회와 요청자 결정 답변.
   - 남의 요청 조회, 다른 레포의 diff, 수락·취소·승인은 여전히 할 수 없다.
   - 허브는 프로토콜 `1`과 `2`를 함께 받는다. 새 경로는 `2`에서만 쓸 수 있으므로 팀원이 동시에 업데이트하지 않아도 된다.
5. **경계는 그대로다.**
   - Office는 `127.0.0.1`에만 열린다. 허브는 Office로 접속하지 않는다.
   - 허브 토큰은 Office 서버에만 있고 화면(브라우저)으로 가지 않는다. Office 로컬 API는 기존 Office 화면의 세션 인증과 쓰기 검사를 쓴다.
   - 받는 쪽 실행은 지금처럼 담당자가 수락해야 시작된다.

## 실패 처리

| 상황 | 동작 |
|---|---|
| 보낼 때 허브 꺼짐 | "허브에 연결할 수 없습니다"를 표시한다. 로컬 기록은 남기지 않고 자동 재시도도 하지 않는다. |
| 응답 유실 뒤 다시 보냄 | 같은 창 키라 허브가 기존 요청을 돌려준다. 중복 생성은 없다. |
| 시간당 상한 초과 | "잠시 뒤 다시 보내주세요"를 표시한다. |
| 답변 전달 실패 | Decisions에 오류를 보여 준다. 다시 시도할 수 있고, 이미 접수된 답이면 "이미 전달됨"으로 표시한다. |
| 상대 질문이 바뀜 | "질문이 바뀌었어요"를 표시하고 새 질문을 다시 띄운다. |
| 원래 작업이 취소·완료됨 | 보낸 요청은 독립적으로 계속된다. 취소는 허브에서 한다. |
| 보낸 요청이 완료됨 | 카드에 완료와 요약을 표시한다. 상대 레포 변경을 내 쪽에 자동 반영하지 않는다. |
| 허브가 프로토콜 1만 지원 | 보내기 버튼을 비활성화하고 "허브를 업데이트해야 합니다"를 표시한다. |

## 불변 조건과 예시

예: app-be Office(관리자)에서 작업 'README 목차'를 보다가 **팀 허브로 보내기**를 누르고 checkout-backend를 고른다. 허브 게시판에 요청자 관리자, 출처 "app-be Office의 작업 'README 목차'"로 요청이 생긴다. checkout-backend 담당자가 수락하고 상대 PM이 질문하면 app-be Office Decisions에 뜨고, 관리자가 거기서 답한다. app-be 카드에는 `↗ checkout-backend · 답변 대기`가 보인다.

다음은 모두 실패해야 한다.
- 연결 토큰으로 남이 보낸 요청이나 다른 레포의 diff를 읽는 것
- 이 레포의 Office가 아닌 곳(브라우저, 다른 레포 Office)에서 보낸 요청에 답하는 것
- G4나 작업 단위 G1에 답하는 것
- 보낸 요청을 Office에서 수락하거나 취소하는 것
- 화면이 허브 토큰을 받는 것
- 같은 창 키로 요청이 두 개 생기는 것

## 범위

- **이번(A·B·C):**
  - 허브: 프로토콜 2, 연결 API(레포 목록, 요청 생성, 보낸 요청 조회와 답변), 요청 출처·생성 키·보낸 곳 레포 칸
  - Office: 로컬 API, 보낸 기록 테이블, 연결 모듈 동기화
  - 화면: 보내기 창, Tasks 카드 표시, 채팅 버튼, Decisions 항목
- **다음 Story:** D(Lead가 계획 중 다른 레포 변경 필요를 초안으로 만들고 사람이 보내기). 그 뒤에 에이전트 간 사실 Q&A.
- **제외:**
  - Office에서 보낸 요청 취소
  - 채팅 문장 해석(모델 호출)
  - 상대 diff 수신
  - 알림, 1단계 후속(IP 고정 등)

## 검증 (V11)

- 자동 테스트로 확인한다.
  - 허브: 연결로 요청 생성, 창 키 중복 방지, (팀원, 보낸 곳 레포) 범위, 시간당 상한, 보낸 요청 조회·답변 규칙(요청자, 옛 질문, G4 거부), 프로토콜 1·2 공존
  - Office: 로컬 API 인증, 연결 모듈의 보낸 요청 동기화와 답변 전달, Decisions 항목 처리
  - 화면(vitest): 버튼 표시 조건, 보내기 창 검증, 카드 표시, Decisions에서 답하기
- 기존 테스트는 전부 통과해야 한다. Office `127.0.0.1` 단언도 유지한다.
- 실제 확인: 이 Mac에서 Office 두 개(app-be는 관리자, 시험용 레포는 다른 팀원)를 허브에 연결하고 다음을 확인한다.
  - app-be에서 보내기 → 상대 수락 → 상대 PM 질문과 G1에 app-be Decisions에서 답하기 → 카드가 완료로 바뀜
- 보안을 포함한 브랜치 전체 리뷰 1회. 결과는 X/X로 보고한다.

## 대안과 복구

- 허브 페이지를 열어 주는 방식: 상태 보기(B)와 Office에서 답하기(C)가 안 돼서 택하지 않았다.
- 화면이 허브를 직접 호출하는 방식: 토큰이 브라우저로 나가고 교차 출처 허용이 필요해서 택하지 않았다.
- 복구: Office를 프로토콜 1 코드로 되돌리면 1단계 동작과 같다. 허브의 새 칸은 비어 있어도 1단계 화면에 영향이 없다.
