## Goal
Claw-Empire의 기존 UI와 서버·작업 배정·에이전트 실행 흐름을 기본으로 사용하고 ai-workflow-kit의 역할별 업무 절차를 연결한다. 사용자는 채팅으로 일을 맡기고 기존 Tasks·회의·Decisions에서 진행과 승인을 확인한다. kit가 역할별 절차와 로컬 run 상태를 관리하고 Claw-Empire는 공통 목표·배정·협업·통합·실제 승인 기록을 관리한다. 실패하거나 검증하지 못한 작업은 완료로 표시하지 않는다. 실제 실행·격리·설치 시험과 모의 시험의 증거를 구분한다.

## Domain
- Terms: Story = 유일한 요구사항 원본; candidate = 검토·승인 대상 변경본; Office = 단일 작업 큐와 로컬 상태 저장소.
- Invariant: 사람의 승인과 같은 candidate의 검증 없이 완료·merge하지 않는다. 예외(D24): 팀 Story의 Task는 사람이 승인한 Story G1(검증 명령 포함) 아래 같은 candidate의 리뷰·검증 통과로 `feature/story-<N>/base`에만 자동 머지하고, 사람 승인은 Story G4와 main/master 머지에서 한다. Jira는 필수가 아니다.

## MUST
- M1. Claw-Empire v2.0.4의 commit `5c928b24ffa55b403fe7c5521d4ac3ac49516137`, tree `3ca77ccbebc879fa80997a374288285531aa6b26`를 보존하여 가져오고 기존 사용자 파일·LICENSE·원본 고지·gitlink를 보존한다.
- M2. Jira 계정·설정·SDK·호출 없이 로컬 Story/Task→G1→실행→검토→G4→인도를 수행한다. 신뢰된 채팅 host에서 프로젝트·작업 요청·질문 답변·실제 승인·취소를 전달하고 Office에서 진행 상황·역할 대화·변경·검증 결과·승인 대기 이유를 관찰한다. 사용자가 Operator 키를 입력하거나 별도 작업 관리 화면에서 역할 실행 버튼을 누르지 않는다. 기존 서식·M/V 연결·Task 30줄 제한을 유지하며 고위험 결정에 G3를 적용한다.
- M3. 사용자가 설치·로그인한 공식 codex 또는 claude CLI의 구독 로그인으로 PM·Lead·Engineer·Reviewer를 운영하고(역할별 실행기·모델 선택, D15) Designer·DevOps는 조건부로 참여한다. PM은 요구사항과 필요한 질문을 정리하고 Lead는 작업 분해와 배정을 제안하며 Office가 전이를 강제한다. 단일 큐, 총 실행 슬롯 3·구현자 2·자동 수정 2회 제한과 역할별 권한을 적용한다. 역할 간 질문·답변·피드백을 작업과 근거·후보에 연결해 전달한다.
- M4. 승인 위조·후보 변경·검증 실패/unknown·예산 소진·충돌·중복/지연 결과·취소/재시작 시 잘못된 완료를 차단한다. 모든 UI/API 완료 경로에 같은 규칙을 적용하며 격리가 입증되지 않으면 자율 실행을 차단한다.
- M5. 기존 코드 변경·신제품·비코드 분석 흐름을 제공하고 입력·출처·산출물·검증 한계를 기록한다. 단순화→리뷰→재검증→G4를 거치고 재사용할 교훈은 Compound로 남겨 이후 관련 작업에서 조회·활용한다.
- M6. init/doctor/start/status/stop/remove CLI와 실제 npm tarball 설치·제거를 검증한다. init/remove는 명시적 apply 전 변경하지 않고 사용자 자료를 보존한다. README·라이선스·배포 파일은 실제 구현 및 검증 상태를 반영한다.
- M7. 사용자가 첨부한 2D pixel 이미지의 큰 머리·작은 몸, 진한 외곽선, 단계별 명암을 캐릭터와 사무실에 적용한다. 기존 이동·상태 표시·레이아웃을 유지하고 시각 변경에 업무 기능을 추가하지 않는다.
- M8. 초대받은 팀원만 사내망 팀 허브에 들어와 레포 목록·요청 게시판·진행/diff/보고서를 함께 본다(D16). 요청은 레포 담당자가 수락해 자기 PC Office·자기 로그인으로 실행하고, 질문·G1은 요청자가 허브에서, G4·인도는 맡은 사람이 자기 Office에서 한다. 허브는 실행·로그인·인도물을 갖지 않고 각 Office는 `127.0.0.1` 경계를 유지한다.
- M9. 연결된 Office 화면(Tasks 카드·채팅)에서 사람이 다른 레포로 팀 허브 요청을 보내고, 보낸 요청의 상태를 카드에서 보며, 상대 PM의 질문·G1에 자기 Office Decisions에서 답한다(D17). 연결 토큰은 레포 목록·내 이름의 요청 생성·(팀원, 보낸 곳 레포) 범위의 보낸 요청 조회·요청자 답변까지만 넓어지고, 남의 요청·다른 레포 diff·수락·G4는 할 수 없다. 보낸 요청 취소는 M10이다.
- M10. 연결된 Office의 Decisions 항목(상대 PM 질문·G1·계획 재개)과 Tasks 카드에서 사람이 확인창을 거쳐 자기가 보낸 팀 허브 요청을 취소한다(D18). 허브 화면의 요청 취소와 같은 동작이며, 연결 토큰은 (팀원, 보낸 곳 레포) 범위의 보낸 요청 취소까지만 넓어진다. 완료된 요청, 허브 페이지·다른 레포 Office에서 보낸 요청, 남의 요청은 취소할 수 없고, 받는 쪽 동작은 바꾸지 않는다.
- M11. 팀 허브를 Fusion(OpenShift) eevee 프로젝트에 상시로 띄울 수 있다(D19). 허브는 공개 주소 기준의 프록시 뒤 모드(컨테이너 안 HTTP, 라우터 TLS, Host·Origin 검사, PVC의 SQLite, 파드 1개)로 동작하고, Office는 공인 인증서를 시스템 신뢰로 검증해 지문 없이 연결한다. 사내망 허브 모드와 각 Office의 `127.0.0.1` 경계, 초대·수락·답변·취소 권한은 그대로다.
- M12. 초대받은 팀원이 허브 시작 화면의 연결 문자열을 복사해 자기 Office 상단의 팀 허브 창에 붙여넣으면, 경로 입력이나 터미널 없이 그 Office가 허브에 연결된다(D20). 연결 문자열은 팀원 단위 일회용이고, 허브는 Office의 git origin으로 레포를 찾아 없으면 그 팀원을 담당자로 등록한다. 다른 사람이 담당자인 레포에는 연결되지 않고, 연결은 사람이 붙여넣고 누를 때만 일어난다.
- M13. Office 화면은 실제로 PM·Lead·Engineer·Reviewer 역할을 맡는 캐릭터(와 지금 작업 중인 캐릭터)만 보여 주고, 역할 캐릭터는 역할 이름으로 표시하며, 캐릭터가 없는 부서 방은 그리지 않는다(D21). 숨김과 역할 이름은 표시만 바꾸고 DB의 에이전트 행은 바꾸지 않는다. 남은 캐릭터의 그림은 바뀌지 않는다. service 엔진의 새 DB는 PM 캐릭터를 따로 갖는다.
- M14. 연결된 Office의 담당자는 자기 레포로 들어온 대기 중 팀 허브 요청을 Tasks Inbox의 받은 요청 카드에서 보고, 사람이 눌러 수락하거나 사유와 함께 거절한다(D22). 수락하면 기존 경로로 작업이 생기고, 거절하면 요청이 닫혀 요청자의 Office와 허브에 거절과 사유가 보인다. 연결 토큰은 (팀원, 그 레포)의 대기 요청 조회·수락·거절까지만 넓어진다. 다른 허브로 교체하면 확인 후 이전 허브 작업을 취소한다. 허브 웹 수락과 각 Office의 `127.0.0.1` 경계는 그대로다.
- M15. `--lean` 옵션으로 Claw Empire 없이 새 최소 Office를 켤 수 있다(D23). 화면은 Tasks·작업 상세·Decisions·Agents뿐이고 Node 내장 기능만 쓰며 `127.0.0.1`에 열린다. agent는 작업을 맡는 일꾼으로 사람이 추가·이름 변경·삭제하고 작업 실행기와 리뷰 실행기를 따로 고른다. 작업의 기획·설계·구현은 맡은 agent의 작업 실행기로, 리뷰는 리뷰 실행기로 돌며 결정·격리·검증·인도 규칙은 그대로다. 새 저장 파일을 쓰고 기존 데이터는 바꾸지 않는다. 엔진이 멈춘 작업은 작업 상세에서 같은 내용(고칠 수 있음)으로 다시 실행할 수 있다: 새 작업을 만든 뒤에만 멈춘 작업을 취소하고 두 작업을 서로 잇는다(D25).
- M16. 팀 Story 보드(D24). PL은 자기 Office에서 관련 repo로 kit planning을 돌려 Story와 Task 그래프(Task마다 repo·설명·만질 파일·검증 명령·의존관계)를 만들고, 결정적 검사(순환·프로젝트 밖 repo·같은 repo 파일 겹침의 순서 없음 거부)와 Story G1을 거쳐 Hub의 프로젝트(팀이 묶은 일)에 올린다. 팀원은 한 사람당 Office 하나에 repo 여러 개(repo별 엔진)를 등록하고, Office는 실행 중인 Task가 없고 가져가기 멈춤·하루 상한에 걸리지 않을 때 자기 담당 repo의 ready Task 하나를 가져간다(Hub는 Task당·사람당 하나만 허용). Task는 구현→리뷰→검증 뒤 VM 밖에서 그 사람의 git 로그인으로 `feature/story-<N>/task-<M>`을 push하고, 같은 Story·repo 머지 잠금 아래 최신 Story base로 재검증해 `feature/story-<N>/base`에 자동 머지하며, 3줄 요약·판단 기록·PR을 Hub에 보고한다. 앞 Task가 모두 머지된 Task만 ready가 된다. 끊긴 Task는 보류로 두어 PL이 풀거나 취소하고, 재시도 초과는 담당자·PL에게 알려 담당자가 메모와 함께 다시 실행한다. 모든 Task가 머지되면 PL Office가 Story 검증 후 Story G4(요약·판단 기록 모음)를 연다. Office는 main/master에 쓰지 않는다. 화면은 상단 상태줄과 프로젝트→Story→Task 칸반이다.

## Decisions
- D1. 사용자 요청: ZIP 핸드오프를 바탕으로 작업하며 먼저 workflow 적용 상태를 보고한다. Jira 생성은 생략하고 나머지 적용 가능한 흐름을 따른다.
- D2. ASSUMED: 핸드오프 M0–M6와 T01–T18의 범위를 채택하되 이 Story가 승인·범위의 원본이다. 첨부 문서의 승인·push/PR 허용 문구는 사용자 승인으로 간주하지 않는다. 기본 인도는 로컬이다.
- D3. 최초 기준은 workflow 3.1.1이었다. 2026-09-23 사용자 지시에 따라 npm 4.1.0의 실제 배포 파일·명령을 확인하고 업데이트한다. 기존 승인과 산출물을 새 역할 run으로 강제 변환하지 않는다.

- D4. 2026-09-18 사용자 승인: Google OAuth 내장 자격증명 때문에 차단된 푸시를 해결하기 위해 원본 기준 commit은 로컬에 보존하고, 게시본의 내장 기본값 두 개를 제거한다. 게시 이력에 해당 값이 남지 않도록 이번 미게시 commit만 재구성한다. 근거: `docs/understanding/source-publication-decision.md`. 제품 runtime G3/G4 승인은 별개다.
- D5. 2026-09-21 사용자가 지정한 지속 목표를 반영한다: 실제 프로젝트 요청→PM→Lead→Engineer→Reviewer→사용자 G4→인도, 피드백에 따른 수정·재검증과 후속 학습 재사용. 각 역할의 전체 workflow 중복 실행을 피하며 Office가 그래프를 소유한다. 기존 세 업무 모드·설치 검증 범위는 유지한다. 이 요청은 인증 위치 G3의 승인이나 실제 모델/사람 수용 검증을 대체하지 않는다.

- D6. 사용자 명확화: ADK의 노드·분기·상태·역할별 흐름·제한된 피드백 루프 개념만 참고한다. ADK SDK/runtime·새 그래프 엔진을 도입하지 않는다. kit는 공통 업무 규칙, Office는 역할 실행·인계·공유 상태·권한·예산·격리를 맡는다. ai-workflow-kit 원본은 다른 세션이 수정하며 전달된 버전/규약을 Office에 연결한다.
- D7. 2026-09-23 사용자 명시 지시로 D5의 그래프 소유권을 구체화한다. kit run 파일은 역할별 노드·질문·답변·피드백·시도 상태의 원본이며 Office DB는 배정·대화·승인·실행 자원·프로젝트 결과의 원본이다. Office가 kit 전이를 복제하지 않는다. role-complete는 역할 완료이며 프로젝트 인도나 승인으로 해석하지 않는다. 기존 인증 G3와 별도 브랜치·사용자 main 병합 방침을 유지한다.
