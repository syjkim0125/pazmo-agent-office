# 결정: 브라우저 하나로 쓰는 팀 흐름 (Hub 웹 중심, 실행은 각자 Mac)

상태: G3 승인(2026-11-04, 사용자 "① 이대로 승인", 설명 페이지 https://claude.ai/artifact/9UGi8rPk9ADHyPcB7prD5F 1판). Story 결정 D41.

## 왜

팀원과 PL이 Figma처럼 주소 하나로 들어와 일을 맡기고 결과를 보게 하고 싶다. 지금은 팀원이 터미널에서 `./office --team`을 켜고, repo를 `team add`하고, 연결 문자열을 붙여 넣고, 실패하면 `team rerun --memo`를 친다. PL은 Story를 올릴 도구가 없다(지금은 스크립트로 Hub API를 부른다). 이 흐름은 개발자에게도 번거롭고 비개발자는 쓸 수 없다.

사용자가 정한 방향(2026-11-04 대화):
- Hub는 늘 떠 있는 곳(지금의 사내 OpenShift)에 두고, 팀원과 PL은 브라우저로 쓴다.
- AI 작업은 지금처럼 **각자 Mac**에서 각자의 claude 구독과 git 로그인으로 돈다.
- 팀원이 할 일은 처음 한 번의 연결뿐이다. 그 뒤에는 터미널을 쓰지 않는다. 설치 명령 한 줄을 한 번 붙여 넣는 것은 받아들인다.
- Task는 AI 리뷰만 거치고 자동으로 끝난다(사람 검토 없음, 지금 D24·D34와 같음).
- Story는 AI 검증까지 자동이고, main에 넣기 전에 PL이 결과를 보고 한 번 승인한다. 고칠 게 있으면 고치는 Task를 더한다.
- PL은 Story를 평소 말로 쓰고, 부족하면 AI가 묻고, AI가 kit Story 템플릿(Goal·MUST·SHOULD·OUT·Decisions·Verify)으로 읽기 쉽게 정리한다. PL이 그것을 승인하면(Story G1) AI가 Task로 나누고, **Task 목록은 PL 확인 없이 바로 올라간다.**

## 목표

1. 팀원: 초대 링크 → Hub 웹 → 처음 한 번 "이 Mac 연결" → 그 뒤로는 웹에서 내 할 일 보기, 작업하기 또는 자동으로 일하기, 결과·실패 보기, 다시 시도.
2. PL: 웹에서 새 Story → AI 질문에 답 → Story 초안 승인 → 자동 Task 나누기·올리기 → 진행 보기 → Story 결과 승인 → main 머지.
3. 각자 Mac의 Office는 로그인할 때 저절로 켜지고, Hub가 시키는 일을 가져가 돌린다.

## 하지 않는 것(non-goals)

- 서버에서 AI 실행(서버의 API 키, 서버의 repo 권한). Hub는 AI도 git도 돌리지 않는다.
- 비밀번호·SSO 로그인, 초대 메일 자동 발송(초대 링크는 관리자가 메신저·메일로 직접 보낸다), 사내망 밖 공개.
- 터미널 없는 Mac 앱(.dmg, 서명·공증). 비개발자까지 넓힐 때 따로 한다.
- 인원·시간(man-month) 단위의 용량 계산. 대신 "자동으로 일하기" 스위치와, 사용 한도에 걸리면 쉬기(D37), 지금의 하루 상한을 쓴다.
- PL이 Task 목록을 올리기 전에 검토·수정하는 화면.
- Windows·Linux·Intel Mac.

## 실패로 보는 것(anti-goals)

- 연결 뒤에도 팀원이 터미널 명령을 쳐야 하는 일이 남는 것(로그인 만료 같은 예외는 웹이 무엇을 할지 쉬운 말로 알려 준다).
- Hub가 claude 키, git 자격, repo 코드를 갖게 되는 것.
- PL 승인 없이 무엇이든 main에 들어가는 것.
- 사용자가 등록한 자기 repo 폴더를 Office가 바꾸는 것(지금 규칙 유지: Office는 자기 체크아웃에서만 일한다).

## 지키는 것(constraints)

- Hub는 Office에 먼저 연락하지 못한다. 웹에서 누른 것은 Hub의 상태만 바꾸고, Mac의 Office가 주기적으로 물어 가져간다(지금 팀 Office의 방식). 웹 화면은 그 상태를 보여 준다.
- 원격 쓰기는 사람의 git·`gh` 로그인으로만 한다. 지금 허용(D24: Task 브랜치 push와 그 PR을 Story base로 머지)에 이 결정이 둘을 더한다.
  - PL의 Office가 Story를 열 때 각 repo에 `feature/story-<N>/base`를 main(프로젝트의 기준 브랜치)에서 만든다.
  - PL이 Story 결과를 승인하면 PL의 Office가 각 repo에서 Story base → 기준 브랜치 PR을 열고 머지 커밋으로 머지한다. 강제 push, 브랜치 삭제는 여전히 없다.
- kit의 Story 계약과 게이트를 그대로 쓴다: Story G1은 PL의 승인 기록이 Story 해시에 묶이고, Story를 고치면 다시 승인받는다. Story 결과 승인은 그 Story의 G4다.
- Hub는 사내 OpenShift에 있고 사내망 전용이다. 사내망 밖에서는 VPN이 필요하다. 로그인은 지금처럼 초대 링크와 30일 쿠키다.
- 공개 저장소: 사내 호스트·조직·repo 이름을 커밋하지 않는다.

## 흐름

### 팀원

1. 관리자가 초대 링크를 보낸다 → 팀원이 열어 수락하면 로그인된다(지금과 같음).
2. 처음 들어오면 **"이 Mac 연결"** 안내가 보인다. 화면의 명령 한 줄을 터미널에 붙여 넣는다.
   - 설치기가 필요한 것(Homebrew 패키지, Node 24, colima·docker, Office)을 깔고, claude와 GitHub 로그인이 없으면 브라우저 로그인을 띄운다.
   - 화면에 짧은 코드가 나오고, 웹에서 **"이 Mac 허용"**을 누르면 그 Mac이 내 계정에 연결된다. 연결은 repo가 아니라 **사람 단위**다. 내가 담당인 repo는 Office가 알아서 자기 폴더에 clone한다.
   - Mac 로그인 때 Office가 저절로 켜지게 등록한다(launchd).
   - 실패하면 무엇을 하라는 쉬운 말과 다시 할 명령을 보인다.
3. 첫 화면은 **"내 할 일"**: 나에게 배정된 Task, 진행 중, 멈춤, 끝난 것. 옆 탭에 프로젝트 → Story → Task 보드.
4. **배정은 자동이다.** PL이나 AI가 사람을 지정하지 않는다. Mac이 연결돼 있고 **"자동으로 일하기"**(기본 켜짐)가 켜진 사람에게, Hub가 그 사람이 권한을 가진 repo의 ready Task를 하나씩 준다. 한 Task는 한 사람만 맡고, 한 사람은 한 번에 하나다. 순서는 Task 그래프(앞 Task가 끝나야 뒤 Task가 ready)와 오래된 것부터다.
   - 예: 사람 A는 repo 셋(be·cart·fe)에, 사람 B는 그중 둘(cart·fe)에 권한이 있다. 둘 다 접속해 있으면 서로 겹치지 않게 각자 할 수 있는 Task가 배정된다.
   - 스위치를 끄면 새로 배정받지 않는다(맡은 Task는 끝까지 한다). 끈 상태에서는 ready Task의 **[작업하기]**로 하나를 직접 고를 수 있다.
5. 상태는 할 일 → 진행 중(구현·리뷰·검증) → 머지 중 → 완료가 저절로 바뀐다. Task 상세에는 3줄 요약, 판단 기록(`ASSUMED:`), PR 링크가 있다.
6. 멈추면 이유가 쉬운 말로 보이고 **[다시 시도]**(메모 칸)가 있다. 사용 한도면 "한도라 쉬는 중, 언제 풀림"을 보인다.
7. 화면 위에 **"내 Mac"** 상태: 일하는 중 / 쉬는 중(한도) / 꺼짐(마지막 확인 몇 분 전).

### PL

1. 프로젝트에서 **[새 Story]**: 하고 싶은 일을 평소 말로 적는다.
2. PL의 Mac Office가 기획을 시작한다(PL의 claude). 부족한 것은 **질문**으로 웹에 뜨고, PL이 웹에서 답한다. 나갔다 와도 이어진다.
3. AI가 kit 템플릿으로 **Story 초안**을 쓴다. 막는 결정(`OPEN BLOCKING`)이 남아 있으면 승인 전에 답으로 받는다(D35 P1). PL은 고칠 점을 적어 다시 쓰게 하거나 **승인**한다(Story G1).
4. 승인되면 AI가 프로젝트의 repo들을 보고 **Task로 나눈다**(repo·할 일·만질 파일·검증 명령·순서). 모든 MUST·Verify가 Task로 덮였는지 검사한다(D35 P5). 통과하면 **바로 올리고 연다**. 각 repo의 Story base도 이때 PL의 Office가 만든다.
5. PL은 보드에서 진행을 본다. 멈춘 Task는 풀거나 취소할 수 있다(지금 Hub에 있는 동작을 웹 버튼으로).
6. 모든 Task가 끝나면 PL의 Office가 **Story 검증**을 저절로 한다: Story base에서 Story의 검증 명령과 AI 리뷰.
7. 결과 화면: 요약, 막는 결정 목록, 바뀐 파일, 검사 결과, AI 리뷰의 지적. PL은 **[고칠 것 추가]**(말로 적으면 AI가 Task로 더함) 또는 **[승인]**.
8. 승인하면 PL의 Office가 repo마다 Story base를 기준 브랜치로 머지한다.
   - 기준 브랜치가 그사이 바뀌기만 했으면 Office가 그것을 Story base에 합치고 Story의 검사 명령을 다시 돌려, 통과하면 머지한다.
   - 충돌이 나거나 기준 브랜치의 보호 규칙(리뷰어·CI)에 막히면 PR을 열어 두고 웹에 "사람이 머지해야 함"과 PR 링크를 보인다.
   - repo마다 따로 머지하고, 모두 머지되면 Story가 완료된다.

## 나눠서 만들기

한 설계, 한 Story 계약 변경, 한 번의 G1로 정하고, 구현은 넷으로 나눠 차례로 한다. 다음 중간점검은 넷을 다 한 뒤다.

| 묶음 | 내용 | 지금 없는 것(조사 결과) |
|---|---|---|
| 1. Mac 연결 | 설치 한 줄, 사람 단위 연결과 웹 승인, 담당 repo 자동 clone·등록, launchd 자동 실행, "내 Mac" 상태 | clone 없음, 백그라운드 실행 없음, 연결은 (사람, repo)마다 문자열 붙여 넣기, 사람 단위 접속 상태 없음 |
| 2. 팀원 웹 | 내 할 일, 보드, Task 상세, 자동으로 일하기 스위치, 작업하기, 다시 시도, 풀기·취소 버튼 | Hub 웹에 Story 화면이 없음. 가져가기 멈춤·다시 실행은 로컬 CLI뿐 |
| 3. PL 기획 | 새 Story, 웹 질문·답, Story 초안과 G1, 여러 repo 기준 Task 나누기, 자동 올리기·열기, Story base 만들기 | Office 기획은 한 project만 봄. Office가 publish·open을 부르지 않음. Story base를 만드는 코드 없음 |
| 4. Story 마무리 | 자동 Story 검증, 결과 화면과 G4 승인, 고칠 것 추가, main 머지 | 검증 Task는 Hub에 있으나 실행하는 Office 없음. main 머지 코드 없음(D24는 Office가 main을 건드리지 않는다고 정함) |

## 정한 것과 만드는 사람에게 맡기는 것

정한 것(사용자):
- 실행은 각자 Mac. Hub는 사내 OpenShift. 설치 한 줄은 받아들임.
- Task: AI 리뷰만, 자동 완료. Story: AI 검증 자동 + PL 승인 한 번 + main 머지.
- PL은 말로 쓰고, AI가 묻고, kit 템플릿으로 정리, PL이 G1 승인, Task는 바로 올라감.
- main 머지: 기준 브랜치가 바뀌기만 했으면 자동으로 합치고 검사를 다시 돌려 머지, 충돌이나 보호 규칙이면 사람에게 넘김(PR 링크).
- 승인 신뢰: 웹에서 PL 본인이 누른 승인을 믿는다. PL의 Office는 승인한 사람이 그 Story의 PL인지, 승인한 Story·결과가 자기가 검증한 것과 같은지 확인하고 기록을 남긴다. Hub 관리자 권한이나 Hub가 뚫렸을 때 머지가 일어날 수 있다는 위험은 받아들이고, 마지막 안전장치는 GitHub의 보호 규칙이다.
- 배정: 사람을 지정하지 않는다. 권한 있는 repo의 남은 Task를 연결된 사람에게 Hub가 자동으로 나눠 준다(위 팀원 흐름 4).

내가 정한 것(바꿀 수 있음):
- 연결은 사람 단위(Mac 하나 = 내 계정), repo는 Office가 clone.
- Story base 만들기와 main 머지는 PL의 Mac에서 PL의 권한으로.
- 용량은 "자동으로 일하기" 스위치 + 한도 쉬기 + 하루 상한.
- 첫 화면은 "내 할 일".
- **repo 권한:** 누가 어느 repo의 Task를 받는지는 Hub의 repo 담당자(지금처럼 관리자가 웹에서 정함)로 정한다. 실제 push·머지는 GitHub 권한이 마지막으로 막는다. PL은 프로젝트의 모든 repo에 담당자여야 Story를 만들 수 있다(기획·Story base·머지에 다 필요).
- **Story 검증에서 AI 리뷰:** 검사 명령이 실패하면 Story 검증 실패(PL이 고칠 것 추가). AI 리뷰의 지적은 막지 않고 결과 화면 맨 위에 보인다. 막을지는 PL이 정한다.
- **고칠 것 추가:** 지금 Story의 MUST·Verify 안의 고침이면 바로 Task로 올린다. 요구가 바뀌면 AI가 Story를 고치고 PL이 G1을 다시 승인한 뒤 올린다.
- **위험도:** PL이 Story를 높은 위험으로 표시하면, G1 뒤 AI가 짧은 설계를 쓰고 PL이 승인(G3)한 다음 Task로 나눈다. 보통 위험은 이 단계가 없다.
- **기획 입력:** 이번에는 글(붙여 넣은 기획 문서 포함)만 받는다. 파일 첨부와 링크를 따라가 읽기는 나중이다. Hub의 입력 한도는 기획 문서가 들어갈 만큼 늘린다.
- **G1·G4 기록:** PL의 Office가 kit의 G1·G4 기록(Story 해시·결과에 묶임)을 자기 쪽에 남기고, 근거로 Hub의 승인 id를 적는다. G4 화면은 동작·지키는 것·확인 범위 세 가지를 보이고 PL은 확인 한 번으로 승인한다.
- **만들고 내보내는 순서:** 네 묶음을 차례로 PR로 머지한다(각각 G4). 각 묶음은 지금의 CLI 흐름을 깨지 않게 더하기만 한다. 사내 OpenShift의 Hub는 네 묶음이 다 들어간 뒤 중간점검 때 한 번 다시 배포한다.

맡기는 것:
- 웹 화면의 모양과 문구(지금 Hub 웹처럼 서버가 만드는 HTML, 스크립트는 최소).
- 설치기가 Office 코드를 받아 오는 방법과 버전 맞추기(Hub와 Office의 프로토콜 버전).
- 사람 단위 연결 토큰의 모양과 지금 (사람, repo) 연결과의 관계.
- 여러 repo 기획의 입력을 만드는 방법(repo별 스냅샷을 어떻게 합칠지).
- Hub가 웹 요청을 Office에 넘기는 큐의 모양과 주기(지금 30초 가져가기 주기 기준).

## 위험과 받아들이는 비용

- **PL Mac 의존:** PL의 Mac이 꺼져 있으면 기획·Story 검증·main 머지가 멈춘다. 웹에 "PL의 Mac 꺼짐"으로 보인다.
- **설치 한 줄:** Homebrew·Xcode 도구가 없는 Mac에서는 설치가 길고 실패할 수 있다. 쉬운 말 오류와 다시 하기로 대응한다.
- **main 머지:** 사람이 읽은 적 없는 AI 코드가 PL 승인 한 번으로 main에 들어간다. PL이 보는 화면에 막는 결정과 검사 결과를 먼저 보인다.
- **사내망 전용:** 밖에서는 VPN이 필요하다.
- **사용량:** 팀원·PL 모두 자기 claude 한도 안에서 일한다. 한도에 걸리면 그 사람의 일만 쉰다.
