## 질문과 답 (2026-10-30)

컨트롤러는 먼저 G4 설명 페이지("부하에서 깨지던 시험")와 대화로 증거를 보였다. 증거는 원인 측정(claw 시작 시간 분포, lean·legacy와의 비교), 고치기 전후의 부하 재현 숫자, 컨트롤러 돌연변이, 전체 시험·타입 검사·Story 검사기, 독립 리뷰 세 번의 판정, 확인하지 못한 것이다. 이어서 세 질문과 선택지(① claw 120초로 넣기, ② 한도 값만 다르게, ③ 근본 해결까지 미루기)를 냈다. 사용자는 세 질문에 직접 답하지 않고 이렇게 지시했다.

> 너가 알려주고, 승인으로 기록해서 작업내역 다 올리고 머지까지 ㄱㄱ

그래서 컨트롤러가 답을 쓰고(D13 방식), 지시대로 승인으로 기록한다. 사용자는 이 답을 기록 전에 보지 않았다.

1. 동작: Claw Office 시작(`start --claw`, `./office`)은 서비스가 준비될 때까지 최대 120초 기다린다(전에는 15초). CPU가 바쁘거나 메모리가 스왑될 때 15초를 넘던 정상 시작이 이제 실패하지 않는다. 서비스가 죽거나 오류로 답하면 전처럼 바로 실패한다. 정말 멈춘 시작은 15초 대신 120초 뒤에 `Office startup timed out.`으로 보고된다. 그동안 `up`은 아무것도 출력하지 않고, `status`는 unknown, `stop`은 거부한다. legacy·lean·team은 15초 그대로다. claude 역할을 멈추는 동작(취소·시간 초과는 SIGTERM 뒤 6초 유예 후 SIGKILL, 보안 검사 멈춤은 바로 SIGKILL)은 바뀌지 않았다. 바뀐 것은 그 시험이다. 개발하는 쪽에서는 다른 세션과 전체 시험을 같이 돌려도 이 두 무리가 부하만으로 빨갛게 되지 않는다.
2. 규칙과 실패 경로: 대기를 늘리는 것은 CPU에 묶인 claw 시작뿐이다. 늘린 대기 중에도 crash와 오류 응답은 바로 끝나서, 진짜 실패를 숨기지 않는다. CLI로 claw를 켜는 시험의 한도는 claw 대기보다 커야 한다(`STARTUP_MS.claw + 60000`). 짧으면 CLI가 시작 도중 죽어 `start.lock`과 기록 없는 Office가 남는다. claude 멈춤 시험은 컨트롤러의 시계(`setTimeout`)만 mock하고, fake의 진행은 진짜 시계로 표시 파일을 기다려 본다. 6초 유예는 5999ms에 살아 있고 6000ms에 SIGKILL되는 것으로 확인한다. 시계를 얼린 시험은 회귀가 생기면 끝나지 않을 수 있다. 그래서 모든 잠금 시험에 시험 한도를 두고, 시험이 끝나면 fake의 프로세스 그룹을 죽이고, 폴링은 시험 신호로 멈춘다. pid 파일이 비어 있으면 그룹을 죽이지 않는다. 0이면 `kill(-0)`이 시험 프로세스 자신을 죽이기 때문이다.
3. 증거와 한계: lifecycle 두 파일은 16스레드 부하에서 고치기 전 3회 중 1회만 통과했고, 120초로는 5/5(75/75)다. 60초로는 유효한 4회 중 3회였다. claude-controller는 36스레드 부하에서 4회 중 1회 → 6/6(120/120)이다. 컨트롤러 돌연변이 7개와 spawn 실패는 모두 실패로 잡히고 파일이 끝까지 돈다. 전체 시험은 1092/1092(`10a5642`), main을 합친 뒤 1093/1093(`23a1eb0`)이고, 타입 검사와 Story 검사기는 exit 0이다. 독립 리뷰 세 번에서 두 번의 지적을 반영한 뒤 "머지 가능"을 받았다. 확인하지 못한 것은 다음과 같다. 측정 범위보다 센 부하에서는 120초도 넘을 수 있다. 실제 전체 시험 두 벌 동시 실행은 하지 않고 부하 루프로 대신했다. claw 시작 자체를 빠르게 하지 않았다. 120초 동안 안내가 없다. 리뷰 후속(빈 pid 읽기 경쟁, fake pid 경로가 `$HOME` 아래, helper 정리의 `kill(0)` 위험)과 실패 기록이 없는 다른 한도도 그대로다.

선택: ① 승인 후 머지. 사용자가 머지까지 맡겼다.

## 평가

Story, diff, 시험과 비교했다.

| 항목 | 평가 |
| - | - |
| 동작 | 맞다. claw만 120초, 다른 엔진 15초, crash·오류 응답의 즉시 종료, 멈춘 시작 동안의 `up`·`status`·`stop`이 `src/cli/lifecycle.ts`의 `STARTUP_MS`·`start()`·`stop()`과 같다. 컨트롤러 동작이 그대로인 점도 diff와 같다. 다만 사용자가 쓴 답이 아니다. |
| 불변 조건·실패 동작 | 맞다. 진짜 실패를 숨기지 않는 근거(대기 중 `exit`·`error` 처리), CLI 한도와 `start.lock`, 얼린 시계와 시험 멈춤, pid 0 함정이 시험·리뷰 기록과 맞다. 다만 사용자가 쓴 답이 아니다. |
| 증거 범위 | 충분하다. 고치기 전후 숫자, 60초 시도의 실패, 돌연변이, 전체 시험, 리뷰를 들었고, 측정 범위 밖 부하와 실제 두 벌 동시 실행을 확인하지 못한 것으로 구분했다. |
| 선택 | ① 승인 후 머지. |

남는 한계: 사용자가 세 질문에 답하지 않았고, 컨트롤러 답을 **보기 전에** 승인으로 기록하라고 지시했다. 그래서 초안을 확인한 뒤 승인한 앞선 G4(#35·#40·#42)보다도 근거가 약하다. 이 기록은 사용자의 이해를 보여 주지 않는다. 사용자가 변경을 받아들이고 머지를 맡겼다는 사실만 보여 준다. 이 답이 G4다.
