# 검증 기록: 브라우저 팀 흐름 묶음 3 (PL 기획)

Story: D41 · D35(P1·P5) · M16 · V19. 결정은 [hub-web-team-flow-decision.md](../understanding/hub-web-team-flow-decision.md)(G3 2026-11-04)의 "PL" 흐름 1–4와 "나눠서 만들기"의 묶음 3이다. 계획은 [2026-11-05-1600-feat-pl-planning-plan.md](../plans/2026-11-05-1600-feat-pl-planning-plan.md), kit 실행은 `.ai-workflow/runs/U38-pl-planning.json`이다. 사용 안내는 [LOCAL-PREVIEW.md의 "PL 기획(새 Story)"](../LOCAL-PREVIEW.md#pl-기획새-story)이다.

이 묶음은 PL이 Hub 웹의 **[새 Story]**에 하고 싶은 일을 적는 데서 팀원이 가져갈 수 있는 Task가 생기는 데까지다. 새 프로젝트, 새 Story, 웹의 질문·답, Story 초안과 **G1**, 높은 위험이면 설계와 **G3**, 그 뒤 PL Mac의 팀 Office가 저절로 하는 Task 나누기(D35 P5 검사) → Hub에 올리기 → 레포마다 `feature/story-<N>/base` → 열기다. 기획 기록의 정본은 Hub이고(새 `PlanBoard`), 웹에서 누른 것은 그 기록만 바꾼다. PL의 Office는 프로토콜 3 연결의 새 경로 셋으로 일을 빌려(lease) 한 단계씩 하고, 모델은 기존 PM/Lead 역할 프로필로 엔진의 단독 실행 자리에서 돈다. Story 검증·결과 화면·G4·main 머지(묶음 4)는 이 묶음 밖이다.

**자동 시험만 마쳤다. 실제 Mac, 실제 claude, 실제 GitHub 원격, 사내 OpenShift 허브와 두 사람의 Mac으로는 돌려 보지 않았다(아래 "실제 확인 계획").** 그래서 실제 확인 전에는 PL에게 쓰라고 안내하지 않는다. 머지는 G4 질문 관문 뒤에 정한다.

- **실제 claude로 돌린 기획의 질.** 실제 PM이 쓸모 있는 질문을 1–3개로 묻는지, 막는 결정(`openBlocking`)을 알맞게 쓰는지, kit 틀의 초안이 검사를 통과하는지. 실제 Lead가 상한(작업 Task 1–20, 검사 1–8, 파일 1–50, Task 명세 16384바이트: 한글이면 약 18KB가 될 수 있다)과 P5를 지키는지, 같은 파일을 만지는 Task에 순서를 두는지, "두 번 나눴지만 검사를 통과하지 못했습니다"가 얼마나 자주 나오는지, 높은 위험 설계가 16KB 안에 드는지. 실행 한 번의 시간 제한 안에 끝나는지.
- **실제 VM에서의 기획 실행.** `planTurn`은 읽기 전용 VM의 `ContainerPlanner`로 여러 repo의 candidate를 `/candidate/tree/<폴더>`에 놓고 돈다. 시험은 가짜 런타임이다.
- **큰 실제 repo의 입력 크기.** 파일 1만 개·100MB 상한, 풀기 시간과 git 30초 제한, Git LFS와 `core.autocrlf`(풀기가 사람의 git 설정을 따른다), 목록이 16MiB를 넘는 큰 repo.
- **실제 GitHub 원격.** 보호 규칙·ruleset이 걸린 원격에 Story base 만들기, 사람의 credential helper로 하는 push. 시험은 로컬 bare origin(거절은 pre-receive 훅)이다.
- **실제 브라우저.** 붙여 넣은 긴 한글 기획 문서(CRLF), `<pre>`의 줄바꿈과 좁은 화면, 두 번 누르기와 뒤로 가기.
- **실제 시간.** claim tick 30초, 하트비트 60초, 빌림 10분, "보통 1분 안"이 실제로 맞는지.
- **실제 OpenShift 허브와 두 사람의 Mac.** 라우터 뒤의 1 MiB POST와 Origin·CSRF, Mac 연결(LaunchAgent)로 켜진 PL Office의 기획, 회사 GitHub Enterprise repo.
- **증거의 경계.**
  - kit G1·G3 기록(`g1.json`·`g3.json`)은 PL Mac의 기획 폴더에 남는 감사 기록이다. kit 역할 그래프는 팀 기획에서 돌지 않는다(계획 "판정과 다르게 한 것" 6). 승인한 Story 본문의 `hub-approval:` G1 줄은 Task 계약에 글로만 들어가고, 그것을 읽는 kit G1 검사는 없다(Task 7 리뷰의 교차 확인).
  - G3의 해시는 그려진 설계 글에 묶이고, 그 글 끝의 "나누기 지문"(나눈 결과 전체를 정해진 순서로 적은 JSON의 sha256)이 Task 명세·파일·검사 명령·Story 검사까지 덮는다. Office는 올리기 전에 저장된 나누기에서 지문을 다시 계산해 맞춰 본다. G3 화면은 "올라갈 Task 전부 보기"에 그 전부를 보인다(마지막 리뷰 뒤 H4).
  - 승인자 = PL은 Hub가 세션으로 정한 member id를 믿는다. Office는 그 id가 기획의 PL인지와 해시·같은 글만 확인한다.
- Story 검증·결과 화면·G4·main 머지·고칠 것 추가와 열린 Story의 웹 취소(묶음 4). Mac 토큰 길의 기획 전달, 알림, 화면 저절로 새로 고침, 파일 첨부, 링크 API `publishStory`의 repo 담당자 검사(기존 그대로).

**사람에게 보이는 한계(리뷰가 미룬 것 중에서).** 아래는 알면서 두었다. 고칠지는 마지막 리뷰와 G4가 정한다.

- **AI가 보는 코드는 기획을 시작할 때의 것이다**(ASSUMED). 입력 candidate는 기획마다 한 번 만든다. Story base는 Story를 처음 올린 직후의 기준 브랜치 끝이라, AI가 읽은 코드보다 새 커밋일 수 있다. 오래 둔 기획은 옛 코드를 보고 나눈다.
- **기준 브랜치가 원격에 없으면 첫 기획 단계가 "PL Mac에서 레포를 받지 못했습니다."로 멈춘다**(자세한 이유에 레포 이름과 git의 말). 프로젝트는 만든 뒤 고칠 수 없으므로 맞는 기준 브랜치로 새 프로젝트를 만들어야 한다. `feature/story-`로 시작하는 기준 브랜치 이름은 프로젝트 만들기에서 거절된다.
- **긴 답은 Story의 Decisions에 500자까지만 남는다.** `PL 답:` 줄은 Office가 한 줄로 접고 500자에서 "…"로 자른다(Task 5). 답 전체는 Hub의 기획 기록과 기획 화면에 남고, AI에게는 줄바꿈을 접은 한 줄로 전체가 간다.
- **설계 다시 쓰기는 없다**(ASSUMED). 마음에 들지 않으면 취소하고 새 Story로. 승인 뒤 나누기가 실패하면 다시 시도만 있다.
- **화면이 저절로 새로 고쳐지지 않는다**(ASSUMED). 기획 화면의 "새로 고침"을 쓴다.
- **base를 만들다 멈추면 이미 만든 다른 repo의 base 브랜치가 남는다.** 다시 시도는 같은 커밋이면 그대로 쓴다. 취소해도 지우지 않는다(Office는 브랜치를 지우지 않는다, D41).
- **base 브랜치를 누가 손으로 만들거나 옮기면 그 기획은 다시 시도해도 열리지 않는다.** base 커밋은 Hub에 적혀 있어 새 Mac이나 잃은 데이터 폴더에서도 같은 커밋으로 이어 가지만(마지막 리뷰 뒤 H6), 원격 브랜치가 다른 커밋이면 "레포 <이름>에 … 브랜치가 이미 다른 커밋으로 있어 Story를 열 수 없습니다. 다시 시도해도 같습니다. …"가 나온다. 그 브랜치에 팀의 작업이 없을 때만 개발자가 지우거나, 기획을 취소하고 새 Story로 시작한다. 적어 둔 커밋이 PL Mac의 git 정리로 지워졌으면 그 repo 이름을 대며 push가 실패한다. 로컬 `bases.json`이 깨졌으면 Hub에 커밋이 다 있어도 멈춘다. Hub가 base 커밋을 계속 거절하면(`BASES_CHANGED`, 지금은 일어나지 않는 길) 네 번째 시도는 "Hub가 답하지 않아…"라는 맞지 않는 문장이 된다. SHA-256 git repo(64자 커밋 id)는 Hub가 받지 않아 세 번 시도 뒤 멈춘다.
- **기획 시작을 두 번 누르면 기획이 둘 생긴다**(Task 3). 만들기에는 멱등 키가 없다. 하나를 취소한다.
- **답이나 고칠 점이 거절되면 적은 글이 사라진다**(Task 3). `INVALID`(예: 공백만 적은 답)는 일반 오류 화면으로 가고 폼에 돌아오지 않는다. 새 프로젝트 폼의 거절도 적은 이름·고른 repo·기준 브랜치를 남기지 않는다.
- **나누는 중에 취소를 눌렀는데 Story가 이미 열렸으면 취소되지 않는다.** 기획은 열림으로 끝나고 그 Story로 가는 링크와 "Story #N이 이미 열려 기획은 끝났습니다."가 보인다(마지막 리뷰 뒤 H2). 열린 Story를 웹에서 멈추는 버튼은 묶음 4이고, 지금은 그 Task를 하나씩 취소한다.
- **한 PL의 Office가 둘이면 한 기획은 먼저 가져간 Office 하나만 맡는다**(마지막 리뷰 뒤 H5). 다른 Office는 그 단계가 끝나거나 빌림이 10분 동안 소식 없이 끝날 때까지 그 기획을 가져가지 않는다.
- **기획은 시작할 때의 프로젝트 레포만 쓴다**(마지막 리뷰 뒤 H3). 시작한 뒤 더한 레포에는 Task가 가지 않는다. 레포나 기준 브랜치가 바뀌었거나 PL이 담당자가 아니게 되면 승인은 거절되고, 이미 승인한 기획은 그 레포를 이름 대며 멈춘다(고친 뒤 다시 시도).
- **멈춤·하루 상한에 걸린 팀 Office도 기획 일이 있을지 보려고 실행기를 확인한다**(마지막 리뷰가 미룸). 가져가기는 그대로 막히지만, 묶음 1·2 때와 달리 실행기 확인(CLI 실행)이 주기적으로 일어난다.
- **기획 단계를 한 tick에서는 그 tick의 Task 되찾기를 하지 않는다**(마지막 리뷰가 미룸). Hub가 PL에게 맡긴 Task를 로컬 기록이 잃었으면, 기획 일이 줄을 서 있는 동안 늦게 되찾는다.
- **보낼 수 없는 결과는 약 10분마다 같은 단계를 다시 한다**(마지막 리뷰가 미룸, 드묾). 그동안 PL의 더 새 기획도 기다린다.
- **Office를 기획 단계 도중 다시 켜면 그 단계가 10분까지 기다린다**(리뷰 2차가 미룸). 빌림에 묶인 Office id가 프로세스마다 새로 생겨, 다시 켠 Office는 앞 빌림이 끝날 때까지 그 기획을 받지 못한다. 그동안 화면은 "AI가 …하고 있습니다"다. 나중에 Office id를 데이터 폴더에 두거나 마지막 소식 시각을 보인다.
- **오래된 두 번째 Mac은 Hub에 적힌 base 커밋을 아직 갖고 있지 않을 수 있다**(리뷰 2차가 미룸). 그러면 push가 "src refspec … does not match any"로 실패하고, 그 레포를 받아 올 때까지 다시 시도도 같다. 나중에 push 전에 받아 온다.
- **빌림이 없는 때는 레포가 없는 Office가 먼저 기획을 가져가 멈출 수 있다**(리뷰 2차가 미룸, H5의 남은 쪽). 나중에 `plan-next`가 그 Office의 준비된 레포를 실어 보낸다.
- **연결되지 않은 레포 줄이 잘못 나올 수 있다**(리뷰 2차가 미룸). 다른 기획의 단계가 180초 넘게 도는 동안에는 줄 서 있는 기획 화면이 실제로 연결된 레포를 이름 댈 수 있다.
- **문구:** 취소 안내는 열린 Story면 기획이 열림으로 끝난다는 것을 말하지 않는다. "프로젝트의 모든 레포 담당자여야"는 실제로 보는 범위(시작할 때 적어 둔 레포)보다 넓게 말한다. `REPOS_CHANGED` 문구는 지금 어떤 화면에서도 할 수 없는 프로젝트 변경을 말한다. Hub는 40자 커밋 id만 받는다(SHA-256 repo는 base 기록이 거절된다).
- **기획 폴더는 지우지 않는다**(마지막 리뷰가 미룸). 기획마다 PL Mac에 최대 100 MiB의 기획 입력이 남는다.
- **다시 시도할 때 이미 올라간 Story를 승인한 본문과 다시 맞춰 보지 않는다**(마지막 리뷰가 미룸). 그 키로는 PL 자신의 연결만 올릴 수 있다. AI의 글에 보이지 않는 방향 바꾸기 문자(bidi)가 들어가는 것도 아직 막지 않는다.
- **Hub가 Office의 멈춤 알림까지 거절하거나 Office가 결과를 네 번 보내지 못하면, 그 기획은 "기획 중"(또는 "설계 중"·"나누는 중")에 머물고 PL의 다른 기획도 10분까지 기다린다**(Task 6 판정). 그동안 Task 가져가기는 계속되고, 빌림이 끝난 뒤 Office가 그 단계를 처음부터 다시 해 본다. 거절된 결과 대신 보낸 멈춤 알림을 Hub가 받으면 기획은 멈춤이 되고 이 기다림은 없다.
- **Office와 Hub 버전이 다르다는 말이 다른 원인에도 나온다**(Task 6·9). "Hub가 이 Office의 결과를 받지 않았습니다(Hub와 Office 버전이 다를 수 있습니다). Office를 업데이트한 뒤 다시 시도하세요."는 Hub가 결과를 400으로 거절한 모든 때에 나온다. Office는 초안 구조(JSON 65536바이트)와 높은 위험의 나누기(JSON 524288바이트)를 보내기 전에 재지 않아서, 버전이 같아도 AI의 출력이 너무 크면 이 말이 된다. 400에 문자열 코드가 없으면 자세한 이유가 `undefined: …`로 시작한다.
- **PL의 Office가 Hub보다 옛 버전이면**(기획을 모름) 기획 화면은 "PL의 Mac이 가져가기를 기다립니다(보통 1분 안)."에 머물고 Mac 줄은 "대기 중"이다. 반대로 Hub가 옛 버전이면 Office 로그에만 한 줄이 남는다(그 Hub에는 기획 화면이 없다).
- **문구가 원인과 맞지 않는 때:** 나누는 중 Hub 연결이 해제되면(401) 세 번 다시 해 본 뒤 "Hub가 답하지 않아 Story를 올리거나 열지 못했습니다. 잠시 뒤 다시 시도하세요."(다시 연결해야 한다)다(Task 8). "설계가 너무 깁니다(16KB 넘음)."에는 다음 할 일이 없다(Task 9). `bases.json`이 안전하지 않은 경로면 기획 입력의 문장("레포에 기획 입력으로 옮길 수 없는 경로가 있습니다.")이 나온다(Task 8). 기획 입력의 `candidate.json`을 쓰다 Mac이 꺼지면 "PL Mac에 만들어 둔 기획 입력이 바뀌었거나 읽히지 않습니다. 다시 시도하고, 또 실패하면 취소한 뒤 새 Story로 시작하세요."인데 다시 시도는 늘 실패한다(Task 4).
- **AI의 입력에서 조용히 빠지는 파일이 있다**(Task 4). 대소문자·NFC만 다른 경로는 둘 다(위 폴더가 겹치면 그 아래 전부) 빠지고, repo 밖을 가리키거나 아무것도 가리키지 않는 링크도 빠진다. 개수는 Office 로그에만 남는다.
- **빠진 링크를 거쳐 가는 링크가 있으면 기획 입력을 얼리지 못할 수 있다**(Task 4, 드묾). 그러면 "레포에 기획 입력으로 옮길 수 없는 경로가 있습니다."나 "PL Mac에 만들어 둔 기획 입력이 바뀌었거나 읽히지 않습니다. …"(자세한 이유에 repo 이름)로 멈추고, 다시 시도해도 같은 나무라 같게 멈춘다. 그 repo의 링크를 고쳐야 한다.
- **보호된 파일이 PL Mac의 기획 폴더에 잠깐 풀린다**(Task 4). `.env` 같은 보호된 파일은 AI의 입력에 들어가지 않지만, 입력을 만드는 동안 `<root>/team/plans/<planId>/tree/` 아래에 다른 파일과 함께 풀렸다가 끝나면 지워진다(폴더는 0700). 그 사이 Office나 Mac이 꺼지면 남는다. 그 기획의 다음 시도가 대개 지우지만, 취소한 기획이나 `candidate.json`을 쓴 직후에 꺼진 경우에는 사람이 지운다.
- **기획 입력을 만드는 git이 사람의 설정을 따른다**(Task 4). Git LFS repo는 풀기가 오래 걸려 30초 제한에 "PL Mac에서 레포를 받지 못했습니다."(repo 이름)로 멈출 수 있다. 목록이 16MiB를 넘는 repo도 "레포가 커서…"가 아니라 이 문장이다.
- **기획 일을 묻는 동안에도 머리글이 "일하는 중"일 수 있다**(Task 6). Office가 30초마다 Hub에 기획 일을 묻는 짧은 동안을 단계로 센다.
- **`team pause`와 하루 상한은 기획을 막지 않는다**(R4 ASSUMED). PL의 Office는 기획 단계 동안 Task를 가져가지 않으므로, 긴 단계(나무 만들기 + 모델 실행)마다 그만큼 Task가 늦는다.
- **PL이 Task를 쥐고 있으면(실패해 다시 시도를 기다리는 것 포함) 기획은 그 Task가 끝나거나 풀릴 때까지 기다린다.** 기획 화면이 그 Task를 이름 댄다.
- **관리자가 아닌 팀원이 체크 없이 취소를 보내면**(손으로 만든 요청) `FORBIDDEN` 대신 "취소하려면 '정말 취소합니다'를 체크하세요."가 먼저 나온다(Task 3, 묶음 2의 Task 취소와 같은 모양).
- 구현 중 Task별 작은 지적 중 코드·시험에만 관련된 것(중복 도우미, 약한 단언, 상수 관계 시험 없음 등)은 사람에게 보이지 않으며 구현 장부에 남아 있다.

## 실제 확인 계획

사용자 확인 뒤에 한다. 공유 허브, 실제 데이터 폴더와 OpenShift 허브 연결이 있는 기존 Office, 회사 repo에는 쓰지 않는다. 그런 것이 필요하면 따로 묻는다. 실제 Mac의 `~/Library/LaunchAgents/com.pazmo.office.plist`를 쓰는 확인은 [묶음 1의 계획](2026-11-04-mac-connect.md#실제-확인-계획) 머리말을 따른다.

### 이번 묶음: 로컬 허브 + 이 Mac(PL) + 시험 팀원 한 명

묶음 1의 "이번 묶음" 준비(로컬 허브, `NODE_EXTRA_CA_CERTS`, 시험용 `--data-dir`)를 그대로 쓴다. 사용자가 PL(관리자)이고, 팀원 A는 **두 번째 시험 데이터 폴더**의 팀 Office를 연결 문자열(`hub-link`)로 붙여 "두 번째 사람" 역할만 한다(Mac 연결이 아니어도 된다). 모델은 실제 claude, 실행은 실제 VM이다.

1. **준비.**
   - GitHub에 작은 시험 repo 둘을 둔다(회사 repo가 아니다). 하나는 기준 브랜치 `main`, 하나는 `develop`이다. 두 repo 설정에서 머지 커밋을 허용한다.
   - 허브에서 PL을 두 repo의 담당자로, A를 두 repo(또는 하나)의 담당자로 한다.
   - PL과 A의 팀 Office에 두 repo를 각각 `team add`·`hub-link`하고 `./office --team`(live)으로 켠다.
   - 10의 "Mac 꺼짐" 줄까지 보려면 PL은 이 Mac을 시험 `--data-dir`로 `mac connect`해 둔다(실제 LaunchAgent를 쓰므로 묶음 1 계획 머리말대로 먼저 묻는다). 하지 않으면 기획 화면의 Mac 줄은 늘 "PL의 Mac: 연결된 Mac 없음"이다.
2. **새 프로젝트.** 보드의 새 프로젝트에서 두 repo와 기준 브랜치(`main`, `develop`)로 만든다. A의 새 프로젝트 화면에는 A가 담당인 repo만 나오는지.
3. **새 Story.** 줄바꿈이 든 수천 자의 한글 기획 문서를 붙여 넣고 위험도 보통으로 기획 시작을 누른다.
   - 1분 안에 "기획 대기" → "기획 중"이 되는지.
   - A의 화면에는 같은 기획이 보이되 버튼이 없는지. A가 한 repo만 담당이면 A에게 새 Story가 보이지 않는지.
4. **질문과 답.** 질문이 나오게 일부러 모호하게 쓴다. 줄바꿈을 넣어 답하고, 답이 기획 화면에는 줄바꿈째 그대로 남고, 다음 초안의 Decisions에는 줄바꿈이 한 칸으로 접힌 `PL 답:` 한 줄로 들어가는지(500자를 넘는 답은 "…"로 잘린다). 막는 결정 표시가 나오면 그것도 본다.
5. **초안·고쳐 쓰기·승인(G1).**
   - 초안이 Goal…Verify 틀이고 `ASSUMED:` 줄이 있는지.
   - 고쳐 써 주세요를 한 번 하고 고친 초안이 그 점을 반영하는지.
   - 두 탭을 열어 한 탭에서 승인한 뒤 다른 탭에서 승인하면 "그사이 기획이 바뀌어…"가 나오고 아무것도 바뀌지 않는지.
6. **나누기·올리기·base·열기.**
   - "나누는 중" → "열림"과 Story #N 링크가 나오고, 보드의 Story에 Task 목록(repo, 순서)이 보이는지. 기획 하나에 Story 하나인지.
   - Story가 쓰는 repo마다 `feature/story-<N>/base`가 기준 브랜치의 그때 끝 커밋에 있는지(`git ls-remote`).
   - PL의 `<데이터 루트>/team/plans/<planId>/`에 `story.md`(`Status: Approved`, `hub-approval:` G1 줄), `g1.json`(`responseRef: hub-approval:<id>`), `bases.json`이 있고, 같은 base 커밋이 Hub 기획 기록에도 있으며, 대상 repo와 사람의 폴더에는 커밋·변경이 없는지.
   - 실제 claude의 질문·초안·Task 나누기가 쓸 만한지, 단계마다 걸린 시간을 적어 둔다.
7. **팀원의 Office가 Task를 가져감.** PL의 자동으로 일하기를 끈다(기획은 계속되는지도 본다). A의 Office가 Task를 가져가 Story base로 PR을 열고 머지하는지(3단계 흐름 그대로).
8. **높은 위험 Story.** 위험도 높음으로 하나 더 만든다.
   - G1 뒤 "설계 중" → "설계 승인 대기"에 설계(계획 + Task 목록, 끝에 "나누기 지문" 줄)가 보이고, [올라갈 Task 전부 보기]를 열면 Task마다 설명·파일·확인 명령과 Story 확인이 보이며, 그때까지 GitHub에 base가 없고 보드에 Story가 없는지.
   - 설계 승인 뒤 그 Task 목록 그대로 열리고, Hub의 Story가 높은 위험이고, `design.md`·`g3.json`이 있는지.
   - A가 그 Task를 보통 Task처럼 돌리는지.
9. **base push 실패 뒤 다시 시도.** Office는 base를 repo 이름 순서(글자 코드 순)로 만들고, Task나 Story 검사가 있는 repo에만 만든다. 그래서 다른 repo의 base가 먼저 생기는 것을 보려면 두 조건이 필요하다: 막는 repo는 이름이 **뒤에 오는** 시험 repo이고, Story가 두 repo 모두에 Task(또는 Story 검사)를 가져야 한다.
   - 두 repo를 다 바꿔야 하는 일을 적고 위험도 **높음**으로 만든다. G3 전에 설계의 Task 목록에서 두 repo가 다 나오는지 본다(아니면 그 기획은 취소하고 다시 적는다).
   - 설계 승인 전에, 이름이 뒤에 오는 repo에 `feature/**` 브랜치 만들기를 막는 규칙(GitHub ruleset의 브랜치 만들기 제한)을 건다. 그다음 설계를 승인한다.
   - 기획이 막힌 repo 이름과 이유로 멈추고, Hub Story는 아무도 가져갈 수 없고(draft), 앞 repo의 base는 이미 있는지(`git ls-remote`).
   - 규칙을 풀고 다시 시도하면 같은 Story 번호로 열리고, 앞 repo의 base가 같은 커밋 그대로인지.
10. **PL의 Mac이 기획을 못 할 때.**
    - PL의 Office를 멈춘 채 새 Story를 만든다. PL이 이 Mac을 `mac connect`해 두었으면, Office를 멈추고 180초가 지난 뒤 "PL의 Mac이 꺼져 있습니다(마지막 확인 N분 전). …"가 나오는지(그 전에는 "PL의 Mac: 대기 중" 같은 마지막 상태다). 연결 문자열로만 붙였으면 "PL의 Mac: 연결된 Mac 없음"이 나오는지. 어느 쪽이든 Office를 켜면 이어 가는지.
    - PL이 실패한 Task를 다시 시도하지 않고 쥐고 있을 때 기획 화면이 그 Task를 "Story #S Task #T"로 이름 대며 다시 시도하거나 풀어야 한다고 말하는지.
    - 기획 단계 도중 Office를 껐다 켜면 그 단계가 10분까지 기다렸다 이어 가고(앞 빌림이 끝날 때까지), Story가 하나인지.
    - 프로젝트 repo 하나를 PL Office에서 `team remove`하고 새 Story를 만들면 그 repo 이름을 대며 멈추는지.
    - `claude auth logout` 뒤 새 Story를 만들면, 기획이 기다리거나(Office가 실행기 준비 안 됨을 이미 안 때) "PL Mac의 AI 실행기(claude)를 쓸 수 없습니다: 준비 안 됨. …"으로 멈추는지. 로그인한 뒤 이어 가거나 다시 시도로 이어지는지.
11. **취소.** 질문 차례나 초안의 기획을 취소한다. "정말 취소합니다" 체크 없이는 눌리지 않는지, A에게는 취소 버튼이 없는지.
12. **멈출 지점.** 7의 Story에서 모든 작업 Task가 머지되면 Story의 검증 Task가 준비되지만 아무 Office도 가져가지 않고 Story는 열림에 머문다(Story 검증·G4·main 머지는 묶음 4). 여기서 멈추고, 보드가 그 상태를 보이는지만 본다.
13. **믿을 수 없는 글.** 프로젝트 이름·기획 제목·하고 싶은 일·답·고칠 점에 `<script>`, `"><img onerror>` 꼴을 넣어 보드·내 할 일·기획 화면에서 글자로 보이는지.

### 중간점검(네 묶음 뒤): 사내 OpenShift 허브와 두 사람의 Mac

사내 OpenShift에 허브를 새 버전으로 다시 띄운 뒤 **두 사람의 Mac**으로 한다. [묶음 1](2026-11-04-mac-connect.md#중간점검네-묶음-뒤-사내-openshift-허브와-두-사람의-mac)과 [묶음 2](2026-11-05-teammate-web.md#중간점검네-묶음-뒤-사내-openshift-허브와-두-사람의-mac)의 중간점검을 그대로 하고, 이 묶음의 것을 더한다. 묶음 4까지 끝난 뒤이므로 Story 하나를 main 머지까지 끝까지 간다.

- PL이 웹에서 새 Story → 질문·답 → G1 → 두 repo에 base → 팀원 Mac이 Task를 가져감 → (묶음 4) Story 검증·G4 → main 머지.
- 높은 위험 Story 하나를 G3까지, base push 실패(회사 GitHub Enterprise의 보호 규칙) 뒤 다시 시도 한 번.
- PL의 Office가 Mac 연결(LaunchAgent)로 켜진 Office일 때 기획이 도는지, 로그인 직후 VPN이 없을 때 기획이 기다렸다가 이어지는지.
- 회사 repo 크기의 기획 입력(파일 1만 개·100MB, LFS)과 걸린 시간.
- 사내 프록시·라우터 뒤에서 새 POST(새 프로젝트·새 Story·답·고쳐 쓰기·승인·설계 승인·다시 시도·취소)가 Origin·CSRF 검사를 통과하고, 1 MiB 본문(새 Story·답)이 라우터를 지나는지.

### 네 묶음 뒤 중간점검이 덮어야 할 것(묶음 1·2·3 합친 목록)

사용자가 요청한 짧은 체크 목록이다. 상세 절차는 위와 앞 두 기록에 있다.
