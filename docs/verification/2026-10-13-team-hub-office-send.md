# 팀 허브 2단계 A·B·C (Office에서 보내기) — 검증 기록

Scope: U10, Story M9·M4, V11, D17.
- G3: [team-hub-office-send-decision.md](../understanding/team-hub-office-send-decision.md) (2026-10-13 승인).
- Plan: [2026-10-13-1200 plan](../plans/2026-10-13-1200-feat-team-hub-office-send-plan.md).
- 1단계 기록: [2026-10-12-team-hub.md](2026-10-12-team-hub.md).

이 기록은 U10의 G4(아래 "G4" 절)까지 담지만 전체 Story 완료를 주장하지 않는다. 커밋 전 작업 트리 기준이다. **같은 Mac에서 한 사용자가 두 Office를 오간 확인이며, 다른 사람의 PC, 회사 IT 정책, 여러 날 운영은 확인하지 않았다.**

## 무엇이 만들어졌나

- **보내기 (A):** 연결된 live Office의 Tasks 카드와 채팅창에 **팀 허브로 보내기** 버튼이 있다. 창에서 대상 레포, 내용(UTF-8 16,384바이트, NUL 금지), 위험도를 고른다. 모델은 부르지 않는다. 창마다 UUID 키가 붙고, 허브는 (팀원, 키)마다 요청을 한 번만 만든다. 연결당 시간당 30건까지다.
- **상태 보기 (B):** 연결 모듈이 5초 주기로 (팀원, 보낸 곳 레포) 범위의 보낸 요청을 받아 `pazmo_hub_outgoing`에 둔다. 카드에 `↗ <레포> · <상태>`가 붙는다. diff는 받지 않고 4줄 요약만 받는다.
- **Office에서 답하기 (C):** 상대 PM의 질문, 범위 승인(G1), 계획 재개가 내 Office Decisions에 `팀 허브 · <레포> · …`로 뜬다. 답은 허브의 요청자 답변으로 전달된다. Office에서는 승인(1번)만 할 수 있고, 거절이나 취소는 허브 페이지에서 한다.
- **권한 (프로토콜 2):** 연결 토큰으로 할 수 있는 일에 레포 목록, 내 이름의 요청 생성, 보낸 요청 조회, 요청자 답변이 더해졌다. 남의 요청, 다른 레포의 diff, 수락, 취소, G4는 여전히 할 수 없다. 허브는 프로토콜 1과 2를 함께 받는다. 허브가 1만 지원하면 버튼은 비활성화되고 "허브를 업데이트해야 합니다"가 표시된다.
- **경계:** 허브 토큰은 Office 서버에만 있다. 화면은 Office 로컬 API(`/api/hub/*`)만 부르고, 보내기와 `hubout:` 답변에는 세션 CSRF 토큰이 필요하다. Office는 계속 `127.0.0.1`에만 열린다.

**리뷰에서 찾아 고친 결함** (각각 테스트를 먼저 쓰고 고쳤다):
- **`hubout:` 답변이 전달되지 않음:** 화면이 결정 ID를 URL 인코딩하는데 서버 경로는 인코딩된 채(`hubout%3A…`)라 허브 답변이 게이트웨이에 닿지 않았다(실험으로 확인). 서버에서 디코딩하고, 잘못된 인코딩은 409 `STALE_APPROVAL`로 돌려준다.
- **`hubout:` 항목이 스냅샷으로 샘:** 허브에서 받은 작업의 스냅샷에 내가 보낸 요청의 결정이 섞일 수 있었다. 스냅샷에서 `hubout:` 항목과 작업 없는 항목을 뺀다.
- **Office에서 보낸 요청을 취소할 수 있었음:** Decisions 항목의 2번 선택이 허브 요청을 취소했다. 결정 문서의 불변 조건("보낸 요청을 Office에서 취소하는 것은 실패해야 한다")에 따라 Office와 허브 양쪽에서 1번만 받는다.
- **전달된 답이 상대 Office에서 거부되면 조용히 사라짐:** 허브가 마지막 거부 결과를 함께 내려 주고, 항목에 "이전 답변이 전달되지 않았어요"를 붙인다.
- **옛 허브에서 버튼이 숨겨짐:** 결정 문서대로 비활성화하고 안내 문구를 보인다.
- **응답 유실 뒤 재전송 시 작업 연결이 사라짐:** 동기화가 먼저 만든 기록 위에 같은 키로 다시 보내면 작업 ID와 출처가 비었다(실험으로 확인). 기존 기록을 채우는 upsert로 바꿨다.
- 그 밖에: `hubout:` 답변에도 CSRF 요구, 출처의 제어 문자 거부, 반납 후 이전 담당자·상태가 남던 문제, 채팅에서 연 창의 Esc가 채팅 패널까지 닫던 문제, 출처에 폴더 이름 대신 허브 레포 이름 사용.

## 실제 확인 (2026-10-13, Mac 한 대)

- 허브: 192.168.12.141:8443. 같은 CA로 새 코드를 재시작했다.
- 보내는 쪽: app-be Office(관리자, 포트 60368). 새 코드로 재시작했다.
- 받는 쪽: 이번 확인용으로 새로 만든 로컬 레포 `pazmo-hub-test-backend`. origin은 `example.test`이고 푸시하지 않았다. 이 레포의 Office(포트 60400)를 띄워 팀원 "테스트" 담당으로 허브에 등록하고 연결했다.

- 카드 표시는 Office 로컬 API가 읽는 보낸 기록으로 확인했다. 카드 화면 자체는 컨트롤러가 캡처하지 않았다. 표시 규칙은 화면 테스트로 확인했다.

## 확인하지 않은 것

- 다른 사람의 실제 PC에서 보내기와 답하기
- 옛 허브(프로토콜 1)와 새 Office가 섞인 실제 운영. 자동 테스트로만 확인했다.
- 시간당 상한, 응답 유실 뒤 재전송, 허브가 꺼진 상태에서 보내기. 자동 테스트로만 확인했다.
- 채팅창에서 보내기. 화면 테스트로만 확인했다.
- 상대 PM이 질문(`questions`)이나 계획 재개를 올리는 경우. 자동 테스트로만 확인했다. 이번 실제 확인에서는 PM이 바로 G1을 올렸다.

- 허브 쪽: 같은 키에 다른 내용으로 다시 보내면 처음 요청을 조용히 돌려준다. 마이그레이션이 트랜잭션 밖에서 돈다(허브 프로세스는 하나).
- Office 쪽:
  - 허브가 꺼져 있으면 보내기 실패까지 약 30초 걸릴 수 있다(호출 두 번).
  - 4000자 자르기가 서로게이트 쌍을 가를 수 있다.
  - 동기화와 항목 삭제가 겹치면 다음 주기에 스스로 복구된다.
  - 잘못 라우팅된 404도 로컬 결정을 지운다.
  - `HUB_NOT_LINKED` 등이 409로 응답한다.
- 화면 쪽:
  - "이미 전달됨"(`already`)을 따로 표시하지 않는다.
  - 결정 본문의 링크는 일반 텍스트다.
  - 성공 문구는 `created:false`일 때도 로컬에서 고른 레포 이름을 쓴다.
  - 보내는 중에 창을 닫으면 키를 버린다.
  - 카드가 다른 열로 옮겨지면 창이 닫힌다.
  - 일시 오류 때 표시가 깜박인다.
  - `role=dialog`, `aria-modal`, ✕의 `aria-label`이 없다.

## G4 (2026-10-13, 사용자 답변)

질문은 동작, 불변 조건 또는 실패 동작, 증거 범위 세 가지다. 컨트롤러는 설명만 했고 답은 사용자가 직접 썼다.

> 이제 내 office화면 안에서 다른 레포에 일 맡길 수 있어. 내 offcie에서는 상대 요청을 승인만 할 수 있고, 거절이나 취소는 허브에서만 해. 다른 사람의 실제 PC는 아직 안봤어.

| 항목 | 평가 |
| - | - |
| 동작 | 충분. Office 화면에서 다른 레포로 보내는 핵심을 짚었다. 카드 상태 표시와 Decisions에서 답하기는 빠졌다. |
| 불변 조건 | 충분. "Office에서는 승인만, 거절·취소는 허브"는 결정 문서의 불변 조건이며, 최종 리뷰가 이 규칙이 깨진 결함을 찾아 고친 부분이다. 실패 동작은 언급하지 않았다. |
| 증거 범위 | 보완 필요. 확인 못 한 것(다른 사람 PC)은 맞다. 확인한 것(한 Mac·Office 두 개 실제 흐름, 자동 테스트)과 회사 IT 정책 미확인은 빠졌다. |

사용자는 평가를 본 뒤 "피드백 확인 후 승인"이라고 답했다(D13 방식). 이 답이 U10의 G4다.
