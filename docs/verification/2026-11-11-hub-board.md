# 검증 기록: Hub 칸반 보드와 로컬 올리기

Story: D42 · M16 · V20. 결정과 계약은 [pazmo-agent-office-contract.md](../understanding/pazmo-agent-office-contract.md)의 D42, 설계는 [hub-board-local-upload-plan.md](../understanding/hub-board-local-upload-plan.md)(G3), 계획은 [2026-11-11-1400-feat-hub-board-plan.md](../plans/2026-11-11-1400-feat-hub-board-plan.md), kit 실행은 `.ai-workflow/runs/U39-hub-board.json`이다. 사용 안내는 [LOCAL-PREVIEW.md의 "칸반 보드와 로컬 올리기"](../LOCAL-PREVIEW.md#칸반-보드와-로컬-올리기)이다.

## 판정으로 정한 것 (동작을 정한다)

- 로그인 전에 열린 주소에 `?…`가 있으면 쿼리는 버리고 경로만 기억해 돌아온다. 자동으로 일하기 스위치를 누르면 `/?mine=1`이 `/`로 돌아간다(허용 경로에 쿼리가 없다).
- "내 Story만"은 내가 PL이거나 내가 맡은 카드가 있는 Story다. 이미 합친 카드도 내 일로 센다.
- 실패한 Task는 실패한 칸(진행 중·리뷰)에 그대로 있다(칸이 바뀐 시각도 그대로).
- 카드의 Mac 상태는 머리줄과 같은 글자를 쓴다("꺼짐(4분 전)").
- 색은 사람이 움직여야 할 때만 "답해 주세요"다(웹 기획 질문·초안·설계 승인, 승인 대기 Story).
- 올리기 경로 두 개에서만, 해제된 Mac이 만든 연결의 토큰은 401이 아니라 `NOT_YOUR_MAC`(403)이다. 새 Mac을 연결한 PL이 옛 Mac에서 올리면 "지금 연결된 Mac에서 다시 실행하세요"를 보게 하려는 것이다. 명령은 옛 연결이 401을 받으면 빈 올리기를 한 번 불러 이 오류와 `UPLOAD_LINK`를 가른다.
- 알 수 없는 프로젝트는 담당자 검사 전에 404다. Story base는 Story가 아직 기획 중일 때만 새로 기록하고(같은 값 다시 보내기는 늘 된다), 올린 Story가 이미 `upload:` 키로 있는데 올리기 기록이 없으면 `STATE` 409로 거절한다. `upload-bases`도 같은 "지금 Mac" 검사를 한다.
- 웹 [취소]는 올리기로 만든, 아직 기획 중인 Story에서만 된다. 웹 기획의 기획 중 Story는 기획 화면에서 취소한다.
- 명령은 PL이 등록한 clone에서 가져오기와 base push만 한다. 그 clone의 작업 폴더·index·로컬 브랜치·HEAD는 바꾸지 않고, 시험이 이를 고정한다(Office의 Story 체크아웃과 겹치지 않는다).
- G1·G3 JSON 경로는 Story 머리의 경로를 `.ai-workflow/`가 있는 가장 가까운 윗 폴더 기준으로 읽는다. G3 설계 파일은 `.ai-workflow/verification.json`의 `design`에서 가져오고, 거기에 없을 때만 G3 기록의 값을 쓴다.
- Story 제목은 첫 `# ` 제목에서 앞의 "Story:"를 뺀 것이다. 없으면 `UPLOAD_STORY`.
- 계획에 없던 오류 코드(`GIT_FAILED`, `BASE_EXISTS`, `STATE`, `HUB_UNREACHABLE`, `HUB_BAD_RESPONSE`)와 검사(위험 필수, Task마다 V 하나 이상, 확인 id가 덮은 V 안에 있음, Story 모양)를 받아들였다. 더 일찍, 더 쉬운 이유로 거절하기 위해서다.
- Story 글의 CRLF·끝 공백에도 kit이 계산한 해시와 명령의 해시가 같다(`kit hash matches kit storyContract on CRLF`).

## 확인하지 않은 것

- **사내 Hub 재배포.** 새 Hub 화면과 두 경로는 로컬 Hub로만 돌렸다. 사내 라우터·TLS·세션 쿠키(`Secure`)와 함께 돌아가는지, 옛 Office와 새 Hub가 섞일 때(옛 Mac의 올리기 `NOT_YOUR_MAC`)는 보지 않았다.
- **실제 두 Mac.** PL의 Mac에서 올리고 다른 Mac의 Office가 가져가 끝내는 흐름, Mac이 바뀐 PL, 자고 깨는 Mac의 상태 글자가 실제 시간과 맞는지.
- **claude가 쓴 실제 Task 파일.** 시험은 사람이 만든 Task 파일을 쓴다. 실제 claude가 안내(스킬)만 보고 맞는 파일을 쓰고, 오류 메시지를 읽고 스스로 고치는지는 보지 않았다. 안내가 실제로 claude에게 읽히는지(`~/.claude/skills`)도 보지 않았다.
- **시험용 가짜가 아닌 브라우저.** `live.js`는 vm의 가짜 DOM으로만 시험했다. 실제 브라우저의 숨은 탭 이벤트, 입력 중 판단, 긴 한글·이모지 카드와 좁은 화면, 인쇄 같은 것은 보지 않았다.
- **실제 GitHub 원격.** 보호 규칙이 걸린 원격에서 Story base 만들기와 PL 자신의 credential helper push. 시험은 로컬 bare repo다.
- **알림, 회사 로그인(SSO), 최종 승인과 main 머지(묶음 4).** 만들지 않았다.

## 실제 확인 계획

사용자 확인 뒤에 한다. 이 Mac의 로컬 Hub와 시험 repo 둘(회사 repo 아님)만 쓰고, 공유 Hub·실제 데이터 폴더·회사 repo에는 쓰지 않는다.

1. **준비.** 로컬 Hub(`NODE_EXTRA_CA_CERTS`, 시험용 `--data-dir`), 시험 repo 둘(`main`과 `develop` 하나씩), PL(관리자)과 팀원 A를 두 repo의 담당자로. PL의 시험 데이터 폴더로 `mac connect`(실제 LaunchAgent를 쓰므로 먼저 묻는다), A는 두 번째 데이터 폴더의 팀 Office를 `./office --team`으로 켠다. 새 PL Mac의 `~/.claude/skills/pazmo-hub-upload/SKILL.md`가 생겼는지 본다.
2. **보드.** 첫 화면이 보드이고 메뉴가 보드·팀 둘인지, 내 할 일이 `/me`로 남았는지. 로그인 전에 `/stories/<id>`를 연 뒤 로그인하면 그 주소로 가는지.
3. **올리기.** PL이 claude 대화에서 작은 Story를 kit workflow로 쓰고 G1을 받은 뒤 "이 Story 허브에 올려줘"라고 한다. claude가 Task 파일을 쓰고 명령을 부르는지, 성공 결과와 보드의 "로컬 승인 · Mac 이름"을 본다. 같은 명령을 한 번 더 해 `already`인지, Story를 일부러 한 번 틀리게(G1 뒤 글 수정) 해 `UPLOAD_G1`의 문구가 말이 되는지.
4. **가져가기와 칸 이동.** A의 Office가 Task를 가져가고, 보드의 카드가 할 일 → 진행 중 → 리뷰 → 완료로 저절로 옮겨 가는지, 화면을 새로 고치지 않아도 10초 안에 바뀌는지, 입력 중에는 안 바뀌는지, 카드의 맡은 사람·Mac 상태·머문 시간이 맞는지. 일부러 한 Task를 멈추게 해(실패) 멈춤 표시와 이유를 본다.
5. **거절과 취소.** 새 Mac을 연결한 뒤 옛 데이터 폴더에서 올려 `NOT_YOUR_MAC`, 담당자가 아닌 사람의 올리기 `NOT_OWNER`, 열리기 전에 웹에서 취소한 뒤 다시 올리기 `UPLOAD_CANCELLED`. 중간에 push를 막아(예: 원격 훅) 실패시킨 뒤 풀고 같은 명령으로 이어지는지.
6. **웹 기획 병행.** 웹 기획으로 만든 Story와 올리기로 만든 Story가 같은 보드에 함께 보이는지.

## 마지막 리뷰 뒤 고친 것

전체 브랜치 리뷰 두 개(전체 동작, 보안)의 Important 여섯 개와 판정 하나를 고쳤다. 고칠 때마다 시험을 먼저 실패시킨 뒤 고쳤다.

1. **Task 파일의 `normal`로 G3를 건너뛸 수 있었다.** 이제 Task 파일이 `high`이거나, kit 설정(`.ai-workflow/verification.json`)이 `requiresG3: true`이거나, Story에 G3 줄이 있으면 높은 위험이다. 뒤의 두 경우에 Task 파일이 `normal`이면 `UPLOAD_G3`("이 Story는 설계 승인(G3)이 필요한 Story입니다…")로 거절한다. 시험: `team-upload` "normal risk is refused when the Story needs G3".
2. **"취소한 것도 보기"를 켜도 취소한 Task 카드가 안 보였다.** 켜면 Story 줄의 다섯 칸 아래 흐린 "취소됨" 줄에 취소한 카드가 모이고, 카드는 그 Task 화면으로 간다. 시험: `hub-board-page` "cancelled cards show in a strip only with the toggle".
3. **claude 안내가 skill로 읽히지 않을 모양이었다.** `mac connect`가 두는 `SKILL.md`는 이제 저장소의 `skills/pazmo-hub-upload/SKILL.md`와 바이트까지 같고(맨 앞이 front matter), Office가 둔 것인지는 옆의 `.pazmo-managed`(쓴 안내의 sha256)로 안다. 고쳤거나 `.pazmo-managed`가 없거나 링크인 안내·폴더는 건드리지 않는다. 임시 파일로 쓰고 이름을 바꾸며, 실패하면 임시 파일을 지운다. 안내와 LOCAL-PREVIEW의 오류 표에 `STATE`·`HUB_UNREACHABLE`·`HUB_BAD_RESPONSE`를 더했다. 시험: `mac-skill-copy` 다섯 개, `team-mac-cli` "mac connect copies the claude upload guide…".
4. **저절로 업데이트가 열어 둔 접힘을 닫고 고른 글과 포커스를 잃게 했다.** 바꾸기 전에 `<main>`의 열린 `<details>`를 요약 글과 순서로 기억해 바꾼 뒤 다시 열고, `<main>` 안에 고른 글이 있으면 바꾸지 않고 다음 차례에 다시 해 보고, 포커스가 있던 요소에 id가 있으면 그 id로 포커스를 돌려준다. 시험: `hub-live` "keeps open details open across a swap", "skips the swap while text is selected in main", "restores focus by id after the swap".
5. **멈춘 뒤에도 "저절로 업데이트"가 보이고 "새로 고침" 링크가 숨어 있었다.** 멈추면 `html.live`를 떼어 링크가 다시 보인다. 200·304가 아니면 멈추는 것(Review Focus 1)은 그대로다. 시험: `hub-live` "stop takes the live class off so the refresh link shows again".
6. **V20의 "웹 기획 Story와 올린 Story가 같은 보드에" 자동 시험이 없었다.** 웹 기획 경로(기획 → 초안 → 웹 G1 → 기획 키로 올리고 열기)의 Story 하나와 올리기 경로의 Story 하나가 `/`의 같은 프로젝트에 카드와 함께 줄로 보이는지 PL과 팀원 화면에서 본다. 시험: `hub-board-page` "a web-planned Story and an uploaded Story share one board"(board()에서 `upload:`나 `plan:` Story를 빼면 실패하는 것을 확인).
7. **(판정) Hub가 보낸 사람이 말하는 Story 해시를 그대로 믿었다.** Hub는 이제 `kitStoryHash(body)`를 다시 계산해 다르면 400 `INVALID`("Story 글과 해시가 맞지 않습니다…")로 거절한다. 시험: `hub-story-upload` "refuses a Story hash that is not the kit hash of the body". 다른 올리기 시험은 고정 해시 대신 글의 kit 해시를 보내도록 바꿨다.
