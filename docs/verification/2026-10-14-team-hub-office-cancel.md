# Office에서 보낸 팀 허브 요청 취소 — 검증 기록

Scope: U11, Story M10·M4, V12, D18.
- G3: [team-hub-office-cancel-decision.md](../understanding/team-hub-office-cancel-decision.md) (2026-10-13 승인).
- Plan: [2026-10-13-1730 plan](../plans/2026-10-13-1730-feat-team-hub-office-cancel-plan.md).
- 앞 단계: [2026-10-13-team-hub-office-send.md](2026-10-13-team-hub-office-send.md) (D17, PR syjkim0125/pazmo-agent-office#18).

이 기록은 U11의 G4(아래 "G4" 절)까지 담지만 전체 Story 완료를 주장하지 않는다. 기준은 PR syjkim0125/pazmo-agent-office#21의 커밋 `d671ffb`이다. **같은 Mac에서 한 사용자가 두 Office를 오간 확인이며, 다른 사람의 PC와 회사 IT 정책은 확인하지 않았다.**

## 무엇이 만들어졌나

- **취소 위치:**
  - Decisions의 `팀 허브 · <레포> · …` 항목(상대 PM 질문, 범위 승인(G1), 계획 재개)에 2번 **요청 취소**가 생겼다.
  - Tasks 카드의 `↗ <레포> · <상태>` 표시 옆에 ✕(보낸 요청 취소)가 생겼다. ✕는 대기·맡음·실행 중·답변 대기일 때만 보인다.
- **확인:** 두 곳 모두 화면 안에서 "요청을 취소하면 되돌릴 수 없어요. 상대 쪽 작업도 멈춥니다."와 [요청 취소] [돌아가기]로 한 번 확인한다.
- **경로:** 화면 → Office 로컬 API `POST /api/hub/outgoing/:id/cancel`(세션 CSRF) → 연결 모듈 → 허브 연결 API `outgoing-cancel` → 허브의 기존 취소. 맡은 Office는 1단계와 같은 종료 경로로 다음 확인 때 작업을 멈춘다.
- **권한:** 연결 토큰에 더해진 것은 "(팀원, 보낸 곳 레포) 범위의 보낸 요청 취소" 하나다. 허브 페이지나 다른 레포 Office에서 보낸 요청, 같은 레포의 다른 팀원 요청, 남의 요청, 끝난 요청은 취소할 수 없다. `outgoing-answer`는 여전히 1번만 받는다.
- **옛 허브:** 새 경로가 없는 허브는 메시지 없는 404를 돌려준다. Office는 이를 "허브를 업데이트해야 취소할 수 있습니다"로 보여 준다. 범위 밖 요청의 404는 허브의 메시지를 그대로 보여 준다.
- **화면 대화상자 교체 (실제 확인 중 사용자 요청):** Office 화면의 나머지 `window.confirm` 8곳과 `window.alert` 13곳을 공통 화면 확인창·알림(`DialogProvider`)으로 바꿨다.
  - 확인창은 '취소'가 기본 선택이고, Esc를 누르면 취소된다.
  - 알림은 오른쪽 아래에 뜨고, 오류 알림은 닫을 때까지 남는다.
  - 문구는 바꾸지 않았다.
  - `api/core.ts`의 `window.prompt`(관리 모드에서 쓰지 않는 토큰 입력)는 그대로 뒀다.

## 실제 확인 (2026-10-13~14, Mac 한 대)

- 허브는 이 Mac에서 돌렸다. 사내망 IP가 192.168.12.141 → 192.168.8.178 → 192.168.12.141로 바뀌어, 그때마다 허브를 그 IP로 다시 시작하고 두 Office를 다시 연결했다. 인증서 지문은 같다.
- 보내는 쪽은 app-be Office(관리자, 60368), 받는 쪽은 시험 레포 `pazmo-hub-test-backend`의 Office(테스트, 60400)다. 두 Office 모두 새 코드로 다시 시작했다.

| 확인 | 결과 |
| - | - |
| (a) 수락 뒤 Decisions에서 취소 | 사용자가 app-be 카드에서 "README 맨 아래에 '취소 시험' 한 줄 추가"를 보냈다. 컨트롤러가 "테스트"로 수락했다. 상대 PM이 범위 승인(G1)을 올렸고 app-be Decisions에 항목이 떴다. **내장 브라우저에서 요청 취소를 눌렀으나 반응이 없었다.** 콘솔에는 "Page dialog suppressed (confirm) … confirm() returned false"가 찍혔다(아래 발견 1). 사용자가 다른 브라우저로 같은 Office를 열어 Decisions에서 요청 취소를 눌렀다. 허브 요청이 `cancelled`가 됐고, 배정은 `cancelled`로 끝나 종료 확인까지 됐다. 시험 Office의 작업은 `cancelled`로 멈췄고, app-be 기록은 `cancelled`가 되며 질문이 사라졌다. |
| (b) 수락 전 카드 ✕로 취소 | 사용자가 새 요청을 보낸 뒤 아무도 맡기 전에 app-be 카드의 ✕로 취소했다. 허브 요청과 app-be 기록 모두 `open` → `cancelled`가 됐다. 받는 쪽 작업은 생기지 않았다. |

- 화면 대화상자 교체 뒤의 화면 안 확인창은 자동 테스트(jsdom)로 확인했다. (b)를 어느 브라우저에서 했는지와 [돌아가기] 동작은 사용자 보고로 덧붙인다.
- 원본 레포는 바뀌지 않았다. 취소된 요청은 인도되지 않았다.

## 화면 톤 정리 (사용자 요청, 2026-10-14)

밝은 테마에서 카드의 허브 칩(`↗ <레포> · <상태>`)이 거의 보이지 않았다. 원인은 이렇다.
- 밝은 테마는 `bg-indigo-900`을 연한 남색으로 바꾸지만, `text-indigo-200`을 바꾸는 규칙은 없다.
- 그래서 연한 배경 위에 거의 흰 글자가 놓였다.

새로 추가한 허브·확인창 화면 요소의 색을 옆 요소들의 기존 패턴으로 바꿨다. 밝은 테마 규칙이 있는 클래스만 썼고, CSS는 추가하지 않았다.

| 요소 | 맞춘 기준 |
| - | - |
| 칩: 진행 중 | 유형 배지 남색 |
| 칩: 완료 | 유형 배지 청록 |
| 칩: 취소 | 부서 배지 회색 |
| ✕ | 카드의 작은 아이콘 버튼과 같은 크기, 평소엔 회색, 마우스를 올리면 빨강 |
| [요청 취소], 위험 확인 버튼 | 카드의 빨간 중지 버튼 |
| [돌아가기] | "팀 허브로 보내기" 버튼 |
| 오류 문구 | 카드의 기존 경고 문구 |
| 확인창 | 기존 모달 |

- 화면 테스트 151/153(실패 2건은 이전부터 실패하던 테스트), 타입 검사·빌드 exit 0.
- 실제 Office에서 밝은·어두운 테마의 칩과 공통 확인창을 눈으로 확인했다. 확인창은 작업 중지 확인을 띄운 뒤 Esc로 닫았고, 작업은 그대로 남았다.
- 새 요청(`d96460e2`, 대기)으로 ✕와 확인 칸을 확인하다가 **배치 깨짐**을 발견했다.
  - 확인 칸이 칩 옆에 끼어들어 칩이 네 줄짜리 좁은 둥근 덩어리가 됐다.
  - 칩은 한 줄로 두고 길면 말줄임하게 했다. 전체 이름은 마우스를 올리면 보인다.
  - 확인 칸과 오류 문구는 칩 줄 아래 카드 폭 전체 상자로 옮겼다. 상자 색은 Decisions의 안내 상자와 같은 호박색이다.
  - 다시 빌드한 화면에서 정상으로 보이는 것을 확인했다.
  - [돌아가기]로 닫았고, 요청은 `open` 그대로다.

| 발견 | 처리 |

## 확인하지 않은 것

- 다른 사람의 실제 PC에서 취소
- 상대 PM 질문(`questions`)·계획 재개 항목에서 취소, 상대가 막 인도한 순간의 취소, 허브가 꺼진 상태·옛 허브에서 취소. 모두 자동 테스트로만 확인했다.
- 화면 대화상자 교체 뒤 다른 화면들(작업 삭제, diff 병합·폐기, 프로젝트·에이전트·설정)의 실제 브라우저 동작. jsdom 테스트와 빌드로만 확인했다.

## 남긴 minor

- 허브·게이트웨이:
  - 취소 직전에 시작된 동기화가 한 주기 동안 옛 상태와 질문을 되살릴 수 있다. 5초 안에 스스로 고쳐진다.
  - `cancel()`의 오류 매핑이 `remote()`와 겹친다(계획에서 정한 코드).
  - 일부 분기(옛 허브 426, 연결 없음, 404 외 HTTP 거부)는 테스트가 없다.
- 로컬 API: 잘못된 percent-encoding과 503 테스트가 없다. `NOT_FOUND`가 409(범위 거부)와 404(모르는 로컬 경로) 두 가지로 나온다.
- 화면:
  - 진행 중인 5초 조회가 취소된 칩을 잠깐 되살릴 수 있다.
  - Decisions의 취소 실패 안내는 일반 문구이다. 허브의 이유는 오른쪽 아래 알림으로 보인다.
  - 확인창은 호출한 화면의 수명과 묶여 있지 않다(서버가 잘못된 전이를 거부한다).
  - 배경이 `inert`가 아니다.
  - 확인창 호출 지점 세 곳(에이전트 계획 담당 변경, 설정 OAuth 삭제, 프로젝트 삭제)은 전용 테스트가 없다.
  - StrictMode에서 마운트 효과가 confirm을 부르면 닫을 수 없는 확인창이 남을 수 있다(지금은 그런 호출 지점이 없다).

## G4 (2026-10-14, 사용자 답변)

질문은 동작, 불변 조건 또는 실패 동작, 증거 범위 세 가지다. 컨트롤러는 설명만 했고 답은 사용자가 직접 썼다.

> 이제 오피스에서 취소 가능. 내가 보낸 요청만 취소할 수 있어. 이미 끝난 요청이면 끝난 요청이라고 나와ㅏ. 다른 사람의 실제 PC에서는 확인 못했어.

| 항목 | 평가 |
| - | - |
| 동작 | 충분. Office에서 취소할 수 있다는 핵심을 짚었다. 취소 위치(Decisions 요청 취소, 카드 ✕), 확인 칸, 화면 확인창·알림 교체는 빠졌다. |
| 불변 조건·실패 동작 | 충분. "내가 보낸 요청만"은 결정 5의 범위다. 정확히는 "이 Office에서 내가 보낸 것"이다. "끝난 요청이면 끝났다고 나온다"는 실패 처리표와 맞다. |
| 증거 범위 | 보완 필요. 확인 못 한 것(다른 사람 PC)은 맞다. 확인한 것(Office 두 개 실제 취소 두 경로, 자동 테스트)과 회사 IT 정책·질문/옛 허브 취소 미확인은 빠졌다. |

사용자는 평가를 본 뒤 "피드백 확인 후 승인"이라고 답했다(D13 방식). 이 답이 U11의 G4다.
