# 2026-10-21 새 최소 Office 1단계 검증

Story: M15 · V17 · D23. 결정: [lean-office-decision.md](../understanding/lean-office-decision.md). 계획: [2026-10-20-1500-feat-lean-office-phase1-plan.md](../plans/2026-10-20-1500-feat-lean-office-phase1-plan.md). 사용 안내: [LOCAL-PREVIEW.md](../LOCAL-PREVIEW.md#새-office-1단계-시험).

## 구현 범위

- **엔진 연결점(Task 1):**
  - 작업마다 실행기를 고를 수 있게 했다: `Config.chooseRunner(role, taskId)`.
  - 이 값이 없으면 Claw 엔진은 지금과 같다. 순수 함수 `liveRunnerWiring`이 이를 보장하고 시험이 있다.
- **저장과 agent(Task 2):**
  - 저장 파일: `<dataDir>/lean/office.sqlite`. 새 파일은 0600이고, 심볼릭 링크를 거부한다. 다른 프로젝트의 파일이면 `DATA_MISMATCH`다.
  - 표는 엔진이 SQL로 읽고 쓰는 칸만 둔다. 엔진 SQL 17개가 이 표에서 오류 없이 준비됨을 리뷰에서 확인했다.
  - agent에는 작업 실행기와 리뷰 실행기가 있다.
  - 실행기 검증은 기존 규칙을 따른다. 기본 agent 만들기는 CLI가 없어도 실패하지 않는다.
  - 오류 코드: `AGENT_BUSY`, `LAST_AGENT`, `AGENT_NAME_INVALID`, `AGENT_NAME_TAKEN`.
- **파사드(Task 3):**
  - 실행기 고르기: 하위 작업이면 원래 작업까지 올라간다. pm·lead·engineer는 작업 실행기, reviewer(G4 평가 포함)는 리뷰 실행기를 쓴다. agent가 없으면 가장 오래된 agent를 쓴다.
  - 보드는 열 5개다. 단계는 엔진 상태에서 계산한다.
  - 상세: 진행 기록, 결정, diff, 실행기 기록, 인도 위치를 보인다. 결과 요약과 멈춤 이유는 최종 리뷰 수정에서 더했다.
  - 만료된 승인은 다시 발급한다.
  - G4 근거를 준비하는 동안에도 상세가 열린다.
  - 작업 시작에 실패하면 진행 기록에 남는다.
  - 진행 기록 출처는 `task_events` 표 대신 엔진의 `messages`·`task_logs`다(결정 3의 대체).
- **서버(Task 4):**
  - Node 내장 기능만 쓰고 `127.0.0.1`에만 열린다.
  - 요청 검사 순서는 Host 421 → Origin 403 → Sec-Fetch-Site 403 → 세션 쿠키(포트별 이름) 401 → CSRF 403 → 멈추는 중 503 → 본문 1MB 413이다.
  - 수명주기 경로는 Bearer 토큰으로 검사한다.
  - 엄격한 CSP와 nosniff를 붙인다. 예상하지 못한 500은 내용을 숨긴다.
  - 실행기 목록에서 설치 경로를 뺀다. 탐색은 같은 시점 요청을 하나로 합치고 5초 동안 재사용한다.
  - 시간 제한을 둔다.
- **진입점과 CLI(Task 5):**
  - `start --lean`, `up --lean`. `--lean`과 `--claw`를 함께 쓰면 `ARGUMENT`다.
  - 엔진이 다르면 `start`와 `up` 모두 `ENGINE_MISMATCH`이고, 켜진 Office는 건드리지 않는다.
  - `tsx` 없이 `node`로 띄운다. 토큰은 IPC로만 넘긴다.
  - 종료는 여러 번 불려도 한 번만 처리한다. 순서는 쓰기 차단 → 서버 → 엔진 → DB이고 10초 상한이 있다. 시작 도중에 종료하면 연 것만 닫는다.
  - `monitor`는 `{url, access:"local-session"}`이다.
- **화면(Task 6):**
  - 빌드 없는 HTML/JS이고 해시 라우팅으로 화면 네 개를 오간다.
  - DOM은 `el()`로만 만든다. 주소 scheme을 검사하고 `innerHTML`과 기본 대화상자를 쓰지 않는다.
  - 3초 폴링은 입력·대화상자·확인 칸을 지우지 않는다. 대신 "새 내용이 있습니다"를 알린다.
  - 요청을 보내는 중에는 대화상자를 닫지 못하게 해 중복을 막는다.
  - 밝은·어두운 테마와 ko/en을 지원하고, 한국어는 단어 단위로 줄을 바꾼다.

## 최종 리뷰와 수정

브랜치 전체 리뷰(보안 포함, 가장 강한 모델)의 결론은 **With fixes**였다. 보안 핵심, Claw 무변경, 실행기 선택을 우회할 수 없다는 점은 확인했다. Important 4건과 spec 누락 1건을 한 번에 고쳤고, 재검토에서 모두 해결됐다.

1. **엔진의 실행기 목록이 시작 뒤 갱신되지 않던 문제.**
   - 증상: 나중에 로그인한 CLI를 고르면 리뷰 단계에서 복구할 수 없게 거부됐다(재현 1/1).
   - 수정(lean만, Claw 무변경): 작업 만들기, 계획 재개 답, agent 실행기 저장 때 엔진 목록을 새로 확인한다. 엔진에는 캐시 없는 탐색을 준다.
   - 재검토에서 같은 종류의 남은 경우(진행 중 agent의 실행기 변경)를 찾아 함께 고쳤다.
2. Decisions의 작업 링크가 하위 작업을 가리켜 "찾을 수 없음"이 되던 문제를 고쳤다. 링크는 이제 원래 작업(`root_id`)으로 간다.
3. **새 clone에서 `up --lean`이 켜지지 않던 문제.**
   - 원인: 엔진이 vendor의 `ws`를 쓰는데 의존성 설치를 건너뛰었다.
   - 수정: 설치는 하고 빌드만 건너뛴다. `start --lean`은 의존성이 없으면 `NOT_INSTALLED`로 멈춘다.
4. 엔진이 더 진행하지 않는 작업이 "진행"으로만 보이던 문제를 고쳤다. 이제 "멈춤" 표시가 붙고 상세에 이유가 나온다.
5. **결정 6의 "결과 요약" 누락.** 엔진이 남기는 G4 요약 메시지에서 가져온다. 인도 뒤에도 남는다.

함께 고친 작은 항목:
- 내용 16384바이트 제한을 미리 검사하고 맞는 문구로 안내한다.
- 연결이 끊겼을 때 안내 문구를 바로잡았다.

### 실제 확인에서 찾은 것

1. **리뷰어의 pass 보고서를 읽지 못해 작업이 멈췄다(고침, `dc6d213`·`70d3d8a`).**
   - 증상: sonnet 리뷰어가 설명 한 문장 뒤에 ```json 블록으로 `"verdict":"pass"` 보고서를 냈다. 판정이 unknown이 되어 `UNKNOWN_RESULT`로 멈췄고 자동 재실행은 없었다.
   - 원인: claude 출력을 역할 보고서 형식으로 바꾸는 `unfence`(`src/runners/claude-profile.ts`)가 메시지 전체가 블록 하나일 때만 벗겼다. 이 코드는 lean이 아니라 main에 이미 있던 부분이라 Claw Office도 같은 위험이 있었다.
   - 수정: 메시지의 첫 ```가 자기 줄에서 ```json(또는 ```) 블록을 열고, 메시지 끝의 펜스 줄이 닫으면 그 사이를 읽는다. 블록 뒤에 글이 있으면 읽지 않고, 블록이 둘이면 JSON으로 읽히지 않는다. 일부러 거부하던 기존 시험 한 줄을 바꿨다(사용자가 A안으로 결정, 설명 페이지 "리뷰 판정 멈춤").
   - 리뷰(독립, 보고만): `dc6d213`은 Changes needed였다. 메시지 전체에서 ```를 세는 조건이 JSON 문자열 안의 ```까지 막아, 이전 코드가 읽던 보고서를 거부했다. 또 긴 빈 줄에서 정규식이 느려졌다(빈 줄 10만 개에 7.5초). `70d3d8a`에서 둘 다 고쳤다(같은 입력 1ms).
   - 받아들인 한계: 앞의 문장은 버린다. "확인하지 못했다, pass라면 이렇다" 같은 메시지도 블록대로 읽힌다. 리뷰어 지시문은 계속 "JSON만"을 요구한다. 앞선 메시지에 문장+보고서 블록 초안이 있으면 그 턴 전체를 읽지 않는다(기존 엄격 규칙과 같음, 시험으로 고정).
   - 근거: 각 수정마다 시험을 먼저 바꿔 실패를 본 뒤 고쳤다(8/9 → 9/9, 9/10 → 10/10). 멈춘 리뷰 메시지를 그대로 다시 넣으면 `verdict=pass findings=0`. **실제 실행에서는 아직 이 경로를 거치지 않았다.** 재시작 뒤 통과한 리뷰는 JSON만 보냈다.
2. **sonnet 리뷰 요청이 API 안전장치에 한 번 막혔다.** 리뷰어 출력은 사이버보안 안전장치 안내 하나였고 exit 1로 끝났다. Office는 이를 리뷰 fail로 기록하고 구현부터 다시 돌렸으며, 두 번째 리뷰가 통과했다. 실행기·API 오류가 "고칠 결함(fail)"으로 분류되어 재시도 횟수를 쓴다(`src/core/verification.ts`, exit≠0 → fail). 후속 작업 후보다.
3. **멈춘 작업을 다시 돌릴 방법이 없다.** 상세에는 "작업 취소"만 있다. 두 번 취소하고 새로 만들었다. 후속으로 작업 상세의 [다시 실행]을 더했다(D25, [결정](../understanding/lean-rerun-decision.md) · [검증 기록](2026-10-27-lean-rerun.md)).
4. **계획 단계가 OAuth 갱신 실패로 두 번 멈췄다(10-23).** `~/.claude/.oauth_refresh.lock`이 남아 있었다. 잠금이 풀린 뒤 "계획 재개" 결정에 사용자 답("응 재개해")을 넣어 이어갔다. 원인은 10-27에 확인했고 수정했다. 실행기 모델 목록을 읽는 claude를 SIGKILL로 끝내면, 그 claude가 토큰을 갱신하던 중일 때 잠금이 남는다. 근거와 수정은 [stop-claude-model-discovery-without-sigkill.md](../solutions/integration-issues/stop-claude-model-discovery-without-sigkill.md)에 있다.
5. **작업 내용에 리뷰어가 확인할 수 없는 요구를 넣으면 판정이 진짜 unknown이 된다(10-23, 결함 아님).** 컨트롤러가 "실행기가 서로 다른지 확인"을 작업 내용에 넣어 PM이 이를 MUST로 만들었고, 리뷰어는 근거가 없어 unknown을 냈다. 실행기 분리는 Office 실행 기록으로 확인한다.
