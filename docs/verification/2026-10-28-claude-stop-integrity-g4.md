# 2026-10-29 claude 역할을 멈출 때 보안 검사 멈춤은 바로 끝내기 G4

Story: M3 · M4 · D15. 검증 기록: [2026-10-28-claude-stop-integrity.md](2026-10-28-claude-stop-integrity.md). PR syjkim0125/pazmo-agent-office#40. kit graph: `.ai-workflow/runs/U22-claude-stop-integrity.json`(상태 `g4`).

## 질문과 답 (2026-10-29)

컨트롤러는 먼저 G4 설명 페이지("OAuth 갱신 잠금 사고", 3부)와 대화로 증거를 보였다. 증거는 U22 상태, main 대비 바뀐 제품 코드 두 파일, 시험·리뷰 결과, 확인하지 못한 것이다. 그다음 세 질문과 선택지를 냈다. 2초 유예 길이는 그 전에 사용자가 따로 골랐다(6초 + 감독 유예 12초, 추천안). 사용자가 "답 초안 너가 써줘 보고 고칠게"라고 해서 컨트롤러가 초안을 냈다. 사용자는 초안을 고치지 않고 이렇게 답했다.

> 피드백 확인 후 승인

사용자가 승인한 답(초안 그대로):

1. 동작: 멈추는 이유에 따라 다르다. 사용자 취소나 시간 초과면 claude 프로세스 그룹에 SIGTERM을 먼저 보내고, 6초 안에 끝나지 않으면 SIGKILL한다(#36은 2초). 갱신 중인 claude가 정리하고 로그인 잠금을 풀 시간이다. 보통 claude는 0.5초 안팎에 끝난다. 예상 밖 hook 이벤트, 잘못된 init, init 없는 시작, 출력 한도 같은 보안 검사로 멈출 때는 #36 이전처럼 바로 SIGKILL한다. claude가 이미 끝난 뒤 들어온 멈춤도 바로 SIGKILL해서 남은 자식까지 끝낸다. 바깥 감독 코드는 멈춘 뒤 12초를 기다리고, 그 안에 정리가 안 끝날 때만 "정리 확인 못 함"으로 기록한다. 오류 코드는 바뀌지 않고 처음 멈춘 이유가 기록된다.
2. 규칙과 실패 경로: claude는 SIGTERM을 받으면 종료 처리 중에 SessionEnd hook을 실행한다. 이 hook은 설정을 꺼도 남는 관리형 hook일 수 있으므로, Office가 막으려던 코드가 돌지 않게 보안 검사 멈춤에는 종료 처리 기회를 주지 않는다. 취소 뒤 정상 종료 중에 hook이 시작되면 이벤트를 보자마자 SIGKILL한다. 다만 hook은 이미 시작됐으므로 막는 게 아니라 줄이는 것이다. 정상 종료 중에 다른 줄이 나오면 무시한다. 그 줄 때문에 SIGKILL하면 잠금을 풀기 전에 끊겨 잠금이 남기 때문이다. SIGTERM을 무시하는 claude나 자식은 6초 뒤(이미 끝났으면 바로) SIGKILL된다. 경계: 예약 마감을 넘긴 실행은 기록 전에 격리되고, 마감 직전 취소에서 정리가 마감을 넘길 수 있는 구간은 최대 12초로 넓어진다.
3. 증거와 한계: 새 시험 6개가 먼저 실패한 뒤 통과했다. 보안 검사 멈춤에서 종료 처리기가 돌지 않음, 끝난 뒤 취소해도 SIGTERM 무시 자식이 죽음, 종료 중 시작한 hook이 끝까지 못 감, 종료 중 출력이 잠금 해제를 끊지 않음, 2.5초 걸려 잠금을 푸는 claude도 잠금을 풂, 멈춘 뒤 7초에 정리를 마치면 "정리 확인됨"이다. 관련 시험 25/25, 전체 959/959, 타입 검사 0. 독립 리뷰 두 번의 지적을 반영했다. 확인하지 못한 것: 6초가 실제로 충분한지(만료 토큰으로 갱신 중인 실제 claude를 재야 함), 실제 claude가 SIGTERM 때 무엇을 출력하고 SessionEnd hook을 이벤트로 흘리는지. 6초·12초는 리뷰어가 바이너리를 읽고 제안한 값이다.

선택: ① 승인 후 머지.
