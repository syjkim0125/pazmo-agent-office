# 첫 실사용 로컬 알파 — 실행 목표 프롬프트

2026-09-23 검토안. 현재 설치된 kit 4.1.0 및 역할 그래프 핸드오프에 맞춘 다음 실행용 지시다. 이 문서를 작성했다는 이유로 구현·승인·검증 완료 상태를 변경하지 않는다.

```markdown
$workflow

현재 pazmo-agent-office를 이어서, @pazmo/ai-workflow-kit 4.1.0의 역할별 그래프를 실제로 사용하는 “기존 로컬 Git 프로젝트의 작업 한 건을 맡기고 결과를 받는 로컬 알파”를 완성해줘.

목표는 내가 안내된 명령으로 Office를 띄우고, 화면에서 작업을 등록·실행·확인·승인하고 결과물을 받는 첫 실사용이다. 아래 기준을 충족하면 종료해. 전체 제품 완성이나 추가 고도화를 완료 조건에 넣지 마.

## 기존 작업과 승인

- 현재 작업 브랜치 codex/office-kit-role-graphs와 그 작업 디렉터리의 설치된 workflow를 사용한다. 사용자 변경을 보존하고 main은 병합하지 않는다.
- 기존 코드·Story·계획·핸드오프·검증 기록을 핵심 경로 중심으로 한 번 확인한다. 기존 Story에 첫 실사용 마일스톤만 반영하고, 나머지 요구사항은 후속 목록으로 보존한다.
- 기존 G1·G3와 인증 결정을 재사용한다. Mac의 기존 Codex 로그인은 신뢰된 controller만 사용하고, 에이전트의 파일·명령 도구는 검증된 전용 VM에서 실행한다.
- README 인증 안내 pilot의 실제 구현·리뷰·피드백·수정·재검증 증거와 사용자의 “결과 일단 승인할게 넘어가”라는 승인을 보존한다. 같은 결과물에 대한 승인 질문을 반복하지 않는다. 대화상 승인과 Office DB 처리·인도 상태는 구분한다.
- 사용자 발언에 없는 승인 답변이나 이해 설명을 대신 작성하지 않는다. README 승인을 다른 후보나 로컬 알파 전체에 대한 승인으로 확대하지 않는다.

## kit와 Office의 책임

- 확인된 npm 배포본 4.1.0을 기준으로 설치·lock·실제 CLI 지원을 확인한다. 4.0.0으로 내리거나 별도 필요 없이 최신 버전을 추적하지 않는다. kit 원본 저장소는 읽기만 한다. 소스 저장소의 최신 핸드오프·제안 schema와 현재 설치된 패키지의 지원 기능을 구분한다. 문서에 있다는 이유만으로 배포·설치됐다고 판단하지 않는다.
- kit는 맡은 일을 끝내는 절차를, Office는 여러 역할의 일이 하나의 목표로 이어지는 과정을 관리한다.
- kit의 native role run이 역할 내부 노드·전이·질문·재개·피드백·시도의 권위 있는 상태다. Office는 프로젝트·배정·역할 간 인계·실행 프로세스·격리·전역 예산·취소·사용자 승인·최종 인도를 관리한다.
- Office DB에는 kit 실행 참조와 검증 가능한 증거를 연결한다. 같은 역할 상태나 전이 규칙을 독립적으로 복제하지 않는다. 기존 CLI 파일과 Office DB를 대체할 별도 상태 저장소는 도입하지 않는다.
- PM은 요청을 받아 clarify → propose로 Story를 제안한다. 실제 G1 이후 팀장은 승인된 Story로 investigate → plan을 수행한다. Developer는 implement → self-check, Reviewer는 review를 수행한다. 각 역할은 전체 workflow를 반복하지 않는다.
- controller가 kit CLI를 조정하고 에이전트는 배정된 노드만 수행한다. 기존 run·node·token을 이어가며, 질문 후 재개 token과 후보 revision을 실제 API 계약대로 처리한다.
- role-complete는 프로젝트 완료나 사용자 승인이 아니다. Office는 kit 결과·동일 후보의 검사·사용자 승인 증거를 연결한 뒤 인도한다.
- 실제 사용한 API·역할 지침·스킬을 기록한다. CE/Superpowers 등 스킬이 실행 환경에 없으면 허용된 직접 절차와 한계를 명시한다. 설치만으로 사용했다고 주장하지 않는다.
- 핸드오프의 모델 선택 지침은 실제 실행 환경에서 허용되고 검증된 모델 범위 안에서 적용한다. 목록과 기능은 한 번 확인해 재사용하며 역할 이름만으로 고비용 모델을 고정하지 않는다. 현재 실행 경로가 검증된 단일 모델만 지원하면 그 모델을 유지하고 제한을 명시한다. 별도 모델 라우터·모델 비교 실험·추가 에이전트를 이번 완료 조건에 넣지 않는다. 요청한 모델과 실행 메타데이터로 확인한 모델을 구분하고, 확인하지 못한 비용 절감은 주장하지 않는다.
- ADK의 설계 개념만 참고한다. ADK SDK/runtime이나 새 범용 그래프 엔진을 만들지 않는다.
- 필수 API가 부족하면 입력·기대 출력·재현 사례·막히는 사용자 흐름을 기존 전달 문서에 모은다. 규칙 복제나 이중 상태 확정으로 우회하지 않고 독립적인 Office 작업은 계속한다.

## 반드시 연결할 사용자 흐름

1. 문서의 지원 명령으로 Office를 실행한다. 필요한 로그인·VM·kit 설정을 짧게 안내하고 시작 시 준비 상태와 실패 원인을 표시한다. Operator 키와 Codex 로그인 용도를 구분한다.
2. 기존 로컬 Git 프로젝트 한 곳을 실행 명령이나 기존 화면에서 지정하고, 화면에 대상 프로젝트를 표시한다. 새 프로젝트 선택 UI는 필수가 아니다. 사용자가 화면에서 작업을 등록하면 실제 모델 PM이 요구사항을 정리하고 필요한 질문만 한다. 사용자는 화면에서 답하고 제안된 범위를 승인한다. 현재 격리 규칙상 사용할 수 없는 프로젝트 경로는 이유와 지원되는 대안을 안내한다.
3. 실제 모델 팀장이 승인된 요구사항을 바탕으로 실행 계획과 역할 배정을 제안한다. 기존 workflow에서 필요한 사용자 결정만 받은 뒤 화면에서 실행을 시작한다.
4. Developer가 격리된 공간에서 구현한다. Reviewer와 등록된 검사는 동일한 동결 후보를 검증하며, 기존 프로젝트의 사용자 변경을 보존한다.
5. 실제 결함이 있으면 대상 후보·근거와 함께 피드백을 전달하고 수정·재검증한다. 자동 수정은 작업 전체에서 최대 2회로 제한하며 kit 자체 시도 제한도 준수한다. 한도에 도달하면 원인과 선택지를 보여준다.
6. 화면에서 진행 상태, 역할 간 인계·질문·피드백, diff, 검사·리뷰 결과, 승인 대기 이유를 확인한다.
7. G4에서 변경 동작·지켜야 할 규칙·검증 범위와 한계를 먼저 쉽게 설명하고 실제 사용자 답변과 승인 의사를 받는다. 설명은 도와주되 사용자 답변을 대신 만들지 않는다. 이미 받은 답변·승인을 보존하고 같은 문답을 반복하지 않는다.
8. 해당 후보에 대한 실제 승인 후 로컬 결과물과 검사·리뷰·승인 기록을 인도한다. 화면과 문서에 결과물 위치 및 원래 프로젝트에 적용하는 방법을 표시한다. 자동 main 병합이나 공개 배포는 하지 않는다.

첫 사용에 SQLite 직접 수정, 임시 스크립트 조립, 승인 JSON 수작업이 필요하면 미완료다. 정식 실행 명령이 기존 내부 코드를 호출하는 것은 가능하지만 사용자에게 조립을 맡기지 않는다. 필요한 검증된 실행 바이너리·설정과 실행·승인·결과물 기록은 임시 폴더에 의존하지 않는 안내된 로컬 경로에 보존한다. Operator 키를 어디서 확인해 어느 화면에 입력하는지 안내하며, 키 자체를 문서나 Git에 기록하지 않는다.

## 완료 판정과 증거

- 문서의 명령과 화면만으로 기존 실제 프로젝트의 요청 → PM → G1 → 팀장 → 구현 → 리뷰·검사 → G4 → 인도를 한 건 수행한다. 실제 모델 호출·kit 역할 그래프 사용·사용자 입력·후보·검증·인도가 서로 연결된 증거를 남긴다.
- 사용자가 직접 같은 순서로 실행할 수 있도록 한다. 내부 pilot이나 브라우저 fixture만으로 사용자 흐름이 완성됐다고 판단하지 않는다.
- 기존 실제 모델 pilot 증거는 재사용한다. 남은 사용자 흐름 검증을 위한 추가 실제 pilot은 우선 한 건으로 제한한다. 추가 실행은 구체적인 실패나 미확인 기준이 있을 때만 한다.
- 기존 실제 피드백 → 수정 → 재검증 증거를 재사용하며 피드백 출처가 모델 Reviewer인지 controller인지 구분한다. 새 작업이 처음부터 합격하면 결함이나 실패 판정을 만들지 않는다.
- 해당 흐름의 취소·실행 실패·재시작에 대해 잘못된 완료, 중복 모델 실행, 검증되지 않은 인도가 없음을 통합 검사 또는 명시적인 실패 주입으로 확인한다. 안전하게 멈추고 복구 안내를 표시하는 동작도 허용하며 무조건 자동 복구를 요구하지 않는다.
- 실패 주입·모의 검증과 실제 모델 증거를 구분한다. 실제 사용자가 직접 조작하지 않은 부분은 그렇게 밝힌다.

## 구현 범위와 진행 방식

기존 승인 계획을 재사용한다. 현재 기록상 역할별 연결과 화면 실행 제어는 구현됐으므로 다시 만들지 않는다. 남은 작업은 다음 최대 3개 묶음으로 진행하며, 이후 이미 완료된 묶음은 건너뛴다.
1. 실제 G4 답변의 평가 → 승인 기록 → 화면에서 결과물 인도까지 남은 연결.
2. 임시 경로에 의존하지 않는 초기 설정·실행·Operator 인증 안내와 준비 상태 확인.
3. 지원 명령과 화면을 통한 실제 모델 작업 한 건의 인수 검증 및 취소·실패·재시작의 미확인 부분 검사.

- 완료된 부분은 재구현하지 않는다. 내부 진단 도구나 문서 추가보다 사용자 흐름 연결을 우선한다.
- Jira는 생략한다. 변경 영향에 맞는 검사·리뷰·Compound를 수행하고 기존 지식 문서를 재사용한다. 통과한 검사는 변경이나 새로운 우려 없이 반복하지 않는다.
- 같은 원인으로 진전 없는 재시도가 두 번이면 멈추고 원인·필요한 결정·다음 행동을 제시한다. 답변 대기 중 불필요한 모델 실행·반복 확인은 하지 않는다.
- 기존 승인 범위의 되돌릴 수 있는 작업은 자율적으로 진행한다. 새로 필요한 사람의 결정은 검토 가능한 결과와 추천안을 한 번에 제시한다.
- 검증된 변경은 현재 작업 브랜치에 커밋·푸시한다. main 병합은 사용자가 한다.
- 신제품·비코드 업무, 다중 프로젝트 동시 운영, 고급 배정, npm 배포·tarball 검증, 학습 검색 고도화, 무관한 UI 재설계·범용화·최적화는 후속으로 남긴다.

## 시작과 종료 보고

시작 시 “지금 사용할 수 있는 것 / 실사용을 막는 연결 / 최대 3개 구현 묶음”만 짧게 보고하고 진행한다.

완료 시 “구현 완료 / 모의·실패 주입 검증 완료 / 실제 모델·사용자 승인 검증 완료”를 구분하고, 실행 명령·사용 순서·결과물 위치·남은 제약·커밋을 제공한다. 조건을 충족하면 종료한다. 미충족이면 완료라고 하지 말고 정확히 남은 항목과 다음 행동만 표시한다.
```
